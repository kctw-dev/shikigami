# #490 RESEARCH: #452 拆分評估

## 原始 Story 分析

### #452 原始 AC 清單

| AC | 內容 | 性質 |
|---|---|---|
| AC1 | 定義 INFRA 測試的測試類型與邊界（unit / integration / smoke） | 架構設計 |
| AC2 | 至少涵蓋 Sprint 122 三個 INFRA stories 的回歸場景（#423 GitHub App 安裝驗證、#442 unzip 可用性、#424 Node.js 20 遷移 / CI Actions 版本釘定） | 測試實作 |
| AC3 | 測試可在 CI pipeline 中自動執行 | CI 整合 |
| AC4 | 測試失敗時輸出清楚的診斷資訊 | 測試品質 |
| AC5 | 整合進現有 tests/test-*.sh 框架 | 框架整合 |

### 各 AC 獨立性分析

- **AC1（架構設計）**：完全獨立，無依賴，應先行完成作為後續 AC 的設計基礎
- **AC2（測試案例）**：依賴 AC1 定義的測試類型邊界；涉及三個不同的 INFRA stories，工作量最重
- **AC3（CI 整合）**：依賴 AC2 測試案例存在才有意義整合；與 AC2 高度耦合，適合同一子任務交付
- **AC4（診斷輸出）**：可與 AC1/AC5 打包，屬框架層面設計決策
- **AC5（框架整合）**：依賴 AC1 架構設計，與 AC4 同屬框架整合工作，可並行

### 依賴關係圖

```
AC1（架構設計）─┬─→ AC4（診斷輸出）─┬─→ [子任務 1 完成]
               └─→ AC5（框架整合）─┘
                                    └─→ AC2（測試案例）─→ AC3（CI 整合）─→ [子任務 2 完成]
```

## 拆分方案

| 子任務 | Issue # | Title | Size | AC 數 | 依賴 |
|---|---|---|---|---|---|
| 子任務 1 | #494 | INFRA 測試框架架構設計與框架整合 | S (1 pt) | AC1, AC4, AC5 | 無 |
| 子任務 2 | #495 | INFRA 回歸測試案例實作與 CI 整合 | M (2 pts) | AC2a, AC2b, AC2c, AC3 | #494 先完成 |

### 拆分理由

1. **關注點分離**：子任務 1 為設計/框架層，子任務 2 為實作層，兩者責任邊界清晰
2. **size 控制**：原始 M (3 pts) 拆為 S (1 pt) + M (2 pts)，每個子任務均在 M 以內
3. **可獨立交付**：子任務 1 完成後即可產出架構文件，有獨立交付價值
4. **依賴明確**：子任務 2 明確依賴子任務 1，不會有隱性前置工作

## 最小可交付增量

**建議優先排入：#494（子任務 1，S size）**

- AC1 架構定義是整個測試框架的基礎，先行完成可解除後續 AC2/AC3 的設計不確定性

- 完成後可在 Sprint 129 安排 #495 全量實作

**Sprint 128 最小排入組合**：

- #494 + #495（S + M, 3 pts）— 完整方案，等同原始 #452 全量交付
