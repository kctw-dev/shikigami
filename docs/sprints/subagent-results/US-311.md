## 決策摘要

### 為何選 C（擴展 #312 claim 機制）

1. **架構一致性**：與 #312 共用 git refs + flock + stale-detect 架構，一套模式兩種粒度
2. **跨機器支援**：git remote 天然跨機器互斥，為 Kotodama 場景預備
3. **最小新增依賴**：無需額外 MCP Server 或基礎設施
4. **TTL + SessionEnd 統一管理**：檔案鎖 TTL 30 分鐘（比 Issue claim 的 2h 更短）

### 為何不選 A（flock + lock 目錄）

- 僅限單機，Kotodama 跨機器場景失效

### 為何不選 B（MCP Server 集中管理）

- 過度工程，目前 stdio transport 不支援跨進程狀態共享
- 單點故障風險，增加部署複雜度
