# ADR-004：Retrospective Problem 主題比對機制

**狀態**：Accepted
**日期**：2026-03-01
**決策者**：Architect
**挑戰者**：QA Engineer

---

## 背景

US-22「Retrospective 驅動角色權重自動調整」要求框架能自動偵測 Retrospective 中反覆出現的 Problem，並據此調整角色參與權重。AC2 具體規定：連續 2 個 Sprint 出現 QA 相關 Problem，則 QA Review 升級為強制執行。

此機制的核心前提是能判斷某個 Problem 文字是否「屬於特定領域（如 QA）」。這個判斷邏輯構成自動化決策的基礎，直接影響 sprint-planning SKILL.md §3 的 Hard Gate 觸發條件，因此需要 ADR 明確記錄選型理由。

設計張力存在於兩個相互競爭的需求之間：

1. **準確性需求**：Problem 描述使用自然語言，同一類型的問題可能有多種表述（「雙階段審查漏做」、「QA 沒做」、「品質把關不足」），純機械比對容易漏判。
2. **確定性需求**：角色權重調整是自動化決策，同樣的 Retrospective_Log.md 在不同執行時間點必須產生相同的判斷結果。若結果不可重複，自動化機制的可信度喪失。

此外，sprint-review SKILL.md §3 的 Retrospective Analytics 已採用「語義主題歸類」展示趨勢。本決策的機制與之構成上下游關係，需要明確區分「展示用途」與「決策用途」的不同精確度要求。

## 決策問題

Retrospective Problem 主題比對機制應採用哪種方法，判定某個 Problem 文字是否屬於特定領域（如「QA 相關」），以作為角色權重自動調整的觸發依據？

同時需要定義「連續 2 Sprint」的計算基準與重置條件。

## 選項分析

### 選項 A：純字串比對

**實作方式**：Problem 文字包含預定義的單一關鍵字（如「QA」）即判定為該領域。

- 優點：實作最簡單，確定性最高，結果完全可重複
- 缺點：覆蓋率低——關鍵字選取偏窄時，「雙階段審查漏做」、「品質把關不足」等語義相關的 Problem 均無法被捕捉；覆蓋率高度依賴關鍵字的精準選取
- 風險：單一關鍵字是單點設計，若 Problem 表述習慣改變，整個偵測機制失效；修復成本高，需修改 SKILL.md 並重新測試

### 選項 B：LLM 語義比對

**實作方式**：在每次 Sprint Planning 時，以 LLM 即時判斷 Problem 文字是否與目標領域語義相關。

- 優點：語義理解能力最強，能處理各種自然語言變體，覆蓋率最高
- 缺點：確定性為零——同樣的 Retrospective_Log.md 在不同 session、不同 LLM 版本、不同 prompt context 下可能產生不同判斷，角色權重調整結果無法重現
- 風險一：違反自動化決策的可重複性原則；角色權重調整若因 session 差異而不一致，框架可信度喪失
- 風險二：sprint-review SKILL.md §3 已採用語義歸類於「展示」用途（可接受不確定性），若本機制也採用語義比對於「決策」用途，兩者表面相同但精確度要求根本不同，造成設計混淆，風險在下游放大
- 風險三：LLM 模型升級或 prompt 變更時，歷史判斷結果無法稽核回溯

### 選項 C：關鍵字清單比對（採用）

**實作方式**：定義一組明文關鍵字清單，Problem 文字包含清單中任一關鍵字即判定為該領域。關鍵字清單明文化於 sprint-planning SKILL.md，可被人工審查、版本控制，並在 Retrospective 中持續擴充。

QA 領域初始關鍵字清單：`["QA", "審查", "Review", "Code Quality", "Spec Compliance", "雙階段", "品質"]`

- 優點一：確定性高——字串比對結果完全可重複，不受 session 或模型影響
- 優點二：覆蓋率可演進——初始清單涵蓋常見表述，新的表述方式可在 Retrospective 後追加至清單；清單本身透過 git 版本控制，修改歷史可查
- 優點三：可稽核性——任何觸發決策均可追溯至特定關鍵字，利於 QA 驗證與 Retrospective 回顧
- 缺點：仍有漏判可能（Problem 表述未涵蓋在現有清單中），但風險可控（Retrospective 本身即是更新清單的時機）
- 與選項 A 的差異：多關鍵字清單替代單一關鍵字，大幅提升初始覆蓋率，且設計上明確支援演進

## 決策

**採用選項 C（關鍵字清單比對）。**

核心判準為：

1. **決策用途必須確定性優先**：角色權重調整是影響後續 Sprint 執行節奏的自動化決策。若同樣的 Retrospective_Log.md 在不同時間點產生不同結果，框架的自治能力反而成為不確定性的來源，違背設計初衷。
2. **可演進性解決覆蓋率問題**：選項 A 和選項 C 的本質區別在於關鍵字清單的設計是否支援演進。選項 C 明文化清單、版本控制、Retrospective 更新，使覆蓋率缺口有明確的修復路徑。
3. **展示與決策的精確度要求不同**：sprint-review §3 的語義歸類服務於趨勢展示（不確定性可接受），本機制服務於觸發決策（不確定性不可接受）。兩者並用語義比對會混淆設計意圖；選項 C 明確區分兩層的不同要求，設計更清晰。

**連續 2 Sprint 的計算基準定義：**

- **連續的定義**：最近 2 個已完成 Sprint（Sprint N-1 和 Sprint N）的 Retrospective Problem 區塊，均包含至少一個目標領域關鍵字
- **重置條件**：某個 Sprint 的 Retrospective Problem 區塊不包含任何目標領域關鍵字，則連續計數器歸零，從下一個 Sprint 重新累計
- **計算時機**：Sprint Planning 開始時，讀取 Retrospective_Log.md 中最近兩個 Sprint 的 Problem 區塊執行比對

## 實作方式

### 關鍵字清單定義

關鍵字清單定義於 sprint-planning SKILL.md，格式如下：

```yaml
# Role Weight Adjustment — Domain Keyword Lists
domain_keywords:
  qa:
    - "QA"
    - "審查"
    - "Review"
    - "Code Quality"
    - "Spec Compliance"
    - "雙階段"
    - "品質"
```

清單以 YAML 格式嵌入 SKILL.md，便於人工閱讀、git diff 追蹤與 Retrospective 更新。

### 比對演算法

```
函數：contains_domain_keyword(problem_text, domain)
  keyword_list = domain_keywords[domain]
  對每個 keyword in keyword_list：
    若 problem_text 包含 keyword（大小寫不敏感）：
      回傳 True
  回傳 False

函數：check_consecutive_trigger(retrospective_log, domain, n=2)
  recent_sprints = 取 retrospective_log 中最近 n 個 Sprint 的 Problem 區塊
  若 recent_sprints 數量 < n：
    回傳 False（歷史不足，不觸發）
  對每個 sprint_problems in recent_sprints：
    若 sprint_problems 中不存在任何 Problem 包含目標關鍵字：
      回傳 False（連續條件不滿足）
  回傳 True（連續 n 個 Sprint 均有匹配，觸發升級）
```

### Sprint Planning Hard Gate 觸發流程

```
Sprint Planning §3 — Role Weight Check：

1. 讀取 Retrospective_Log.md
2. 對每個監控領域（qa, security, ...）執行 check_consecutive_trigger
3. 若 check_consecutive_trigger(qa) = True：
   - 記錄觸發原因（標注匹配的關鍵字與 Sprint 編號）
   - QA Review 升級為強制（Hard Gate，不可跳過）
   - 將觸發事件寫入本次 Sprint Planning 記錄
4. 若無任何領域觸發：
   - 維持當前角色權重
   - 靜默通過
```

### 關鍵字清單更新機制

```
更新時機：Sprint Review 的 Retrospective 環節
更新觸發：當 Retrospective 記錄的 Problem 未被現有關鍵字捕捉時
更新流程：
  1. SQA 識別漏判的 Problem 表述
  2. 提議新關鍵字
  3. Architect 確認後更新 sprint-planning SKILL.md 的清單
  4. 更新記錄於 Retrospective_Log.md 的 Action Items
```

## Decision Challenge（QA Engineer）

**挑戰**：選項 C 的漏判問題被低估。關鍵字清單的演進依賴「人工識別漏判後再更新」，但漏判本身就代表此 Problem 在本 Sprint 未被計入。若 Sprint N-1 和 Sprint N 都因表述偏差而漏判，升級機制就在最需要觸發的時候沈默——這正是選項 C 最大的設計缺陷。選項 B 雖然不確定，但至少不會系統性地漏掉某一類表述。

**反駁**：此挑戰預設了一個前提：漏判後無修復機會。實際上，選項 C 的設計包含兩層保護機制。第一層是初始清單的廣度——7 個涵蓋不同粒度的關鍵字（角色名稱「QA」、流程動作「審查」、英文縮寫「Review」、具體實踐「雙階段」、概念「品質」），刻意設計為語義重疊的多維度覆蓋，而非單一關鍵字的單點設計。第二層是清單演進機制——每次 Sprint Review 的 Retrospective 環節即是審查漏判的結構性時機，Action Items 直接驅動清單更新。

更重要的是，選項 B 的「語義比對不漏判」是一個理想化的假設。LLM 的漏判是隱性的（你不知道它為什麼沒判出來，也無法重現），而選項 C 的漏判是顯性的（比對日誌可以告訴你哪些 Problem 未匹配任何關鍵字），顯性漏判比隱性漏判更容易修復。確定性機制的漏判有明確修復路徑，不確定性機制的錯誤判斷卻可能在數個 Sprint 後才被注意，且無法稽核根因。
