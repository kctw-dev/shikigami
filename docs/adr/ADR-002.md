# ADR-002：測試框架技術選型

**狀態**：Accepted
**日期**：2026-03-01
**決策者**：Architect
**挑戰者**：QA Engineer

---

## 背景

Shikigami 是一個 Claude Code 插件，其核心交付物為 Markdown 檔案（`skills/`、`commands/`、`agents/`）與少量 Bash 腳本，而非傳統應用程式碼。測試需求因此與常見軟體專案截然不同：驗證的目標是框架結構完整性（檔案存在性、frontmatter 格式、Skill 引用正確性、版號一致性），而非業務邏輯或 API 行為。

目前已落地兩個驗證腳本，皆為純 Bash：

- `scripts/validate-commands.sh`（US-T06）：Command 路由驗證
- `scripts/validate-version.sh`（US-T04）：版號一致性驗證

兩者採用一致的實作模式：`set -uo pipefail`、輔助函式組（`print_pass` / `print_error` / `print_info` / `print_section`）、全域 `EXIT_CODE` 追蹤、`preflight_check → AC 驗證函式 → main → 總結輸出`，exit code 0 = 通過，1 = 失敗。

未來測試 Stories（US-T01 ~ US-T09）包含：Skill 完整性驗證、Agent 完整性驗證、JSON Schema 驗證、交叉引用驗證、CI Pipeline 整合、Intent Routing 測試（Prompt Evaluation）、孤兒文件清理規範。需要決定後續所有測試腳本的技術基礎。

## 決策問題

Shikigami 框架結構驗證測試應採用什麼技術框架？

## 選項分析

### 選項 A：純 Bash 腳本（採用）

延續現有 `validate-commands.sh` / `validate-version.sh` 的模式，每個 US 對應一個獨立的 `scripts/validate-*.sh`，共享輔助函式庫（`scripts/lib/validate-helpers.sh`）。

- 優點：
  - 零外部依賴，任何具備 bash 4+ 的環境（包含 CI runner）無需安裝步驟即可執行
  - 現有兩個腳本已建立清晰的函式模式，US-T01 ~ US-T09 可直接套用，學習成本為零
  - 純文字輸出（`[PASS]` / `[ERROR]` / `[INFO]`）格式對 CI log 友善，易於目視審查
  - 腳本即文件：函式命名和 AC 對應關係直接體現在原始碼中
  - 無版本升級風險，bash 本身穩定性極高
- 缺點：
  - 缺乏專用測試框架的 setup/teardown 生命週期管理，複雜測試場景需自行實作
  - 測試之間的隔離性需手動維護（臨時目錄、環境變數還原）
  - 錯誤訊息格式化能力有限，失敗時的 diff 顯示不如專用框架清晰
- 風險：當腳本數量增長到 9+ 個，函式庫的設計若未事先規範，可能出現重複實作

### 選項 B：BATS（Bash Automated Testing System）

使用 BATS（`bats-core`）建立測試套件，每個 `*.bats` 檔案對應一個驗證領域，輔以 `bats-support` 與 `bats-assert` 函式庫。

- 優點：
  - 提供標準化的 `@test` 宣告語法，`setup()` / `teardown()` 生命週期，測試結構清晰
  - `bats-assert` 提供豐富的斷言函式（`assert_output`、`assert_line`、`assert_file_exist`），失敗訊息詳細
  - TAP 格式輸出原生支援多數 CI 系統的測試結果解析
  - 社群活躍（GitHub 13k+ stars），文件完整
- 缺點：
  - 引入外部依賴：`bats-core`、`bats-support`、`bats-assert` 需透過 git submodule 或 npm 安裝，CI pipeline 需加裝步驟
  - Shikigami 的驗證對象是 Markdown 結構而非函式行為，BATS 的斷言豐富性在此場景幾乎無法發揮
  - 框架學習曲線對新貢獻者形成額外門檻
  - 對現有兩個腳本的遷移成本非零
- 風險：引入 git submodule 管理 BATS 在 Claude Code 環境中增加 Preflight 複雜度

### 選項 C：ShellSpec

使用 ShellSpec 建立 BDD 風格的 Shell 測試套件，以 `Describe` / `It` / `When` / `The` 語法描述測試案例。

- 優點：
  - BDD 語法可讀性高，`Describe "validate-commands"` 的描述即規格文件
  - 支援 mock/stub，對腳本外部呼叫（`git`、`jq`）的隔離能力最強
  - 原生產生 JUnit XML 報告，CI 整合完整
- 缺點：
  - 安裝方式較 BATS 更複雜（curl 安裝或手動下載），在 minimal CI image 上安裝步驟最多
  - BDD 語法風格與現有 Bash 腳本差異最大，兩套風格並存造成認知割裂
  - 社群規模遠小於 BATS，中文資料稀少
  - 為 Markdown 結構驗證引入 mock/stub 能力屬於 YAGNI，增加不必要複雜度
- 風險：若 ShellSpec 版本更新引入不相容變更，在無人維護的情況下遷移成本高

## 決策

**採用選項 A（純 Bash 腳本 + 共享函式庫）。**

理由：

1. **測試對象決定工具選擇**：Shikigami 的驗證對象是檔案系統結構與 Markdown 文字格式，而非函式行為或 API 契約。BATS / ShellSpec 的斷言豐富性在此場景無法帶來實質收益，引入的依賴複雜度卻是真實成本。
2. **現有模式已驗證可行**：兩個已上線腳本在 CI 環境穩定運行，函式模式清晰，US-T01 ~ US-T09 可直接沿用，不存在技術跳躍的必要性。
3. **零外部依賴是 CI 友善的必要條件**：Claude Code 插件的目標環境多元，Bash 4+ 是唯一可靠的共同基礎，無需安裝步驟即可在任何 runner 執行。
4. **共享函式庫解決可維護性問題**：透過提取 `scripts/lib/validate-helpers.sh`，輔助函式集中管理，避免 9 個腳本各自重複實作，同時保留各腳本的獨立可執行性。

**排除方案說明：**

- **BATS 排除原因**：外部依賴（git submodule 管理三個 bats-* 函式庫）增加 CI pipeline 的安裝步驟，而其核心收益（結構化斷言、TAP 輸出）對 Markdown 結構驗證的場景邊際效益極低。在 `validate-commands.sh` 已穩定運行的前提下，框架遷移成本大於收益。
- **ShellSpec 排除原因**：BDD 語法風格與現有 Bash 腳本差異最大，且安裝複雜度最高，社群規模最小。在 mock/stub 能力無實際使用場景的前提下，引入 ShellSpec 屬於 YAGNI 反模式。

## 實作方式

### 目錄結構

```
scripts/
  lib/
    validate-helpers.sh       # 共享輔助函式庫（由各驗證腳本 source）
  validate-commands.sh        # US-T06（已存在）
  validate-version.sh         # US-T04（已存在）
  validate-skills.sh          # US-T01：Skill 完整性驗證
  validate-agents.sh          # US-T02：Agent 完整性驗證
  validate-schemas.sh         # US-T03：JSON Schema 驗證
  validate-xref.sh            # US-T05：交叉引用驗證
  validate-orphans.sh         # US-T09：孤兒文件清理規範
```

### 共享函式庫規範（`scripts/lib/validate-helpers.sh`）

```bash
#!/usr/bin/env bash
# scripts/lib/validate-helpers.sh
# 所有 validate-*.sh 的共享輔助函式
# 使用方式：source "$(dirname "$0")/lib/validate-helpers.sh"

# 呼叫端必須在 source 前宣告：EXIT_CODE=0

print_pass()    { echo "[PASS] $1"; }
print_fail()    { echo "[FAIL] $1"; EXIT_CODE=1; ERROR_COUNT=$((ERROR_COUNT + 1)); }
print_error()   { echo "[ERROR] $1"; EXIT_CODE=1; ERROR_COUNT=$((ERROR_COUNT + 1)); }
print_info()    { echo "[INFO] $1"; }
print_warning() { echo "[WARNING] $1"; }
print_section() { echo ""; echo "--- $1"; }
print_banner()  { echo "=============================="; echo " $1"; echo "=============================="; }

has_frontmatter_field() {
  # 參數：$1 = 檔案路徑，$2 = 欄位名稱（如 name / description）
  # 回傳：0 = 存在，1 = 不存在
  local filepath="$1" field="$2"
  awk '/^---/{c++; if(c==2) exit} c==1' "$filepath" \
    | grep -qE "^${field}[[:space:]]*:"
}
```

### 新腳本命名規範

每個驗證腳本須遵循以下規範，以確保 US-T01 可按此直接實作：

- 檔名：`scripts/validate-<目標>.sh`，目標為複數名詞（`skills`、`agents`、`schema`、`xref`、`orphans`）
- 開頭：`set -uo pipefail` + `source "$(dirname "$0")/lib/validate-helpers.sh"`
- 全域狀態：`EXIT_CODE=0`、`ERROR_COUNT=0`
- 結構：`preflight_check()` → 各驗證函式（以描述性動詞命名，如 `scan_skills()`、`has_frontmatter_field()`、`validate_skill_dir()`，沿用現有腳本慣例）→ `main()`
- 結束：`exit "$EXIT_CODE"`
- Shebang：`#!/usr/bin/env bash`

### US-T01 Skill 完整性驗證（`validate-skills.sh`）的驗證邏輯預期

```
preflight_check：skills/ 目錄必須存在
AC1：掃描 skills/ 下所有子目錄，每個子目錄視為一個 Skill
AC2：每個 Skill 目錄下必須存在 SKILL.md
AC3：SKILL.md frontmatter 必須含 name 欄位
AC4：SKILL.md frontmatter 必須含 description 欄位
exit code：0 = 全部通過，1 = 有 ERROR
```

### CI 整合（US-T07）

所有 `scripts/validate-*.sh` 腳本在 CI pipeline 中依序執行，任一腳本 exit code 非 0 則 pipeline 失敗。無需安裝步驟，CI image 具備 bash 4+ 即可運行。

## Decision Challenge（QA Engineer）

**挑戰**：選項 A 最大的風險是「自行造輪」——當驗證腳本從 2 個增長到 9 個，沒有測試框架的 setup/teardown 機制，每個腳本對臨時目錄的建立與清理都需要重複實作。更嚴重的問題是：`validate-*.sh` 腳本本身沒有被測試，若 `has_frontmatter_field()` 函式邏輯有缺陷，整個驗證體系的可信度存疑。BATS 可以為這些共享函式提供單元測試，防止驗證腳本自身引入 Bug。

**反駁**：「驗證腳本需要被測試」的論述成立，但 BATS 不是必要條件。共享函式庫的正確性可透過兩個機制保障：（1）函式邏輯極簡，`has_frontmatter_field()` 的 awk + grep 組合是可目視驗證的單行邏輯，複雜度遠低於需要單元測試的業務函式；（2）所有驗證腳本在 CI 中對真實 Shikigami 倉庫執行，若函式邏輯錯誤導致 false positive，真實的框架文件會成為整合測試樣本並揭露問題。關於 setup/teardown，`validate-*.sh` 的驗證對象是靜態的 Markdown 檔案，不需要建立臨時環境，此問題在本專案場景中並不存在。引入 BATS 解決一個在本場景中尚未發生的問題，違反 YAGNI 原則。
