# ADR-010：Backlog Source of Truth — GitHub Issues 優先策略

**狀態**：Accepted
**日期**：2026-03-03
**決策者**：Architect
**挑戰者**：QA Engineer
**QA Decision Challenge 結果**：ACCEPT-WITH-CONDITIONS（五個先決條件，全部於本次更新中解決）
**關聯 Issue**：#46（feat: 自動化排程框架 — 衝刺 / 需求入庫 / Planning / 程式碼入庫）
**前置 ADR**：ADR-009（Backlog Intake 自動化技術決策）

---

## 背景

Issue #46 原始設計在「核心決策 — Backlog = GitHub Issues」區塊明確定義：

> - **Source of truth**：GitHub Issues
> - `PRODUCT_BACKLOG.md`：廢除或降級為唯讀快照
> - Sprint Planning 用 milestone / label 標記哪些 Issue 進 Sprint
> - Issue 完成 → close Issue，天然追蹤

然而 ADR-009（Accepted，2026-03-03）與 `skills/backlog-intake/SKILL.md` 的實作走向是相反方向：

| 面向 | ADR-009 實作現狀 | Issue #46 原始設計 |
|------|-----------------|-------------------|
| Source of truth | `docs/prd/PRODUCT_BACKLOG.md`（Markdown 檔案） | GitHub Issues |
| 入庫方向 | GitHub Issues → 拉進 PRODUCT_BACKLOG.md | GitHub Issues 本身即 Backlog |
| Sprint Planning | 從 .md 檔案讀取 Backlog，選 Stories | `gh issue list` + labels/milestones 選 Story |
| 完成追蹤 | Story 狀態標記於 .md | close Issue = Story done |

此外，`skills/sprint-planning/SKILL.md` §6（Subagent 派遣順序）目前指定 PO subagent 讀取 `docs/prd/PRODUCT_BACKLOG.md`、`docs/PROJECT_BOARD.md` 與 `docs/prd/ROADMAP.md` 作為 Story 選取來源；`skills/backlog-management/SKILL.md` 也以 PRODUCT_BACKLOG.md 為核心管理對象。

本 ADR 評估三個選項，決定 Backlog 的 source of truth 架構，以解決 Issue #46 原始設計意圖與當前實作之間的矛盾。

---

## 決策問題

Shikigami 框架的 Product Backlog 應以何者作為唯一真相來源（single source of truth），以支援 Sprint Planning、Story 追蹤與 Backlog 管理的全生命週期？

---

## 約束條件

在評估各選項之前，明確列出不可妥協的約束：

| 約束 | 說明 |
|------|------|
| Issue #46 原始設計意圖 | 使用者明確表示希望回到 Issue #46 的設計，GitHub Issues 應成為唯一 Backlog source of truth |
| gh CLI 可用性 | Pre-flight 已驗證 gh CLI 認證，現有 Skill 已依賴 gh CLI（backlog-intake、sprint-execution）|
| ADR-006 Injection 防護 | 任何讀取 GitHub Issue 內容的流程，必須維持 ADR-006 的 XML 隔離標記要求 |
| ADR-003 Out-of-Sprint Hard Gate | Framework 核心文件（ADR、SDD、SKILL.md）的修改須遵循現有的 Sprint Gate 規則 |
| YAGNI 原則 | 不引入超出當前 MVP 需求的複雜抽象層 |

---

## 選項分析

### Option A：維持現狀（PRODUCT_BACKLOG.md 為 source of truth）

維持 ADR-009 的決策，PRODUCT_BACKLOG.md 繼續作為 Backlog 的唯一真相來源，backlog-intake Skill 負責將 GitHub Issues 轉化並寫入 .md 檔案。

#### 架構現狀

```
GitHub Issues
    │
    │ backlog-intake（單向拉取）
    ▼
PRODUCT_BACKLOG.md ← Source of Truth
    │
    │ sprint-planning 讀取
    ▼
Sprint Backlog（docs/sprints/sprint_N.md）
    │
    │ Story 完成後手動更新狀態
    ▼
PRODUCT_BACKLOG.md（狀態標記 In Sprint / Done）
```

#### 優點

- 不需改動現有 SKILL.md，實作成本為零
- PRODUCT_BACKLOG.md 提供結構化的 RICE 分數、MoSCoW 標籤、Acceptance Criteria，格式豐富
- 離線可讀，無需 gh CLI 即可查看 Backlog
- PO 可在 .md 中進行 Backlog Grooming（排序、補充 AC、RICE 評分）

#### 缺點

- 與 Issue #46 原始設計意圖明確矛盾，架構決策無法反映產品設計哲學
- 雙向同步問題：GitHub Issue 狀態（open/closed）與 PRODUCT_BACKLOG.md 的 Story 狀態（未排程 / In Sprint / Done）需人工維持一致，容易漂移
- Story 完成追蹤需要兩個操作（close Issue + 更新 .md），存在遺漏風險
- backlog-intake 的「入庫」步驟在兩個系統之間建立了一個脆弱的同步橋接層，隨 Sprint 數量增加，維護負擔線性上升
- PRODUCT_BACKLOG.md 的 Story ID（US-NN）與 GitHub Issue number 是兩套並行的識別體系，增加認知負擔

#### 遷移成本

無（維持現狀）。

---

### Option B：GitHub Issues 為唯一 Backlog（Issue #46 原始設計）

廢除或降級 PRODUCT_BACKLOG.md，以 GitHub Issues + labels + milestones 作為 Backlog 的完整管理介面。Sprint Planning 直接透過 `gh issue list` + label 過濾選取 Stories。Issue close = Story done。

#### 架構目標

```
GitHub Issues ← Source of Truth（新需求直接開 Issue）
    │
    │ gh issue list --label "sprint-N" --milestone "Sprint N"
    ▼
Sprint Backlog（選取 Sprint N Issues）
    │
    │ Story 完成 → gh issue close
    ▼
GitHub Issues（closed state = done，天然追蹤）

PRODUCT_BACKLOG.md → 降級為唯讀快照或廢除
```

#### Label 設計（兩層）

Issue 體系分為兩層：原始 Issue（使用者需求）與 Backlog Issue（PO 審查後建立的結構化 User Story）。兩層 Issue 各有對應的 label 集合。

**原始 Issue labels（使用者開立的需求 Issue）**

| Label | 語意 | 設置時機 |
|-------|------|---------|
| `feature-request` | 功能需求類 Issue | PO 分類後套用 |
| `bug` | 缺陷類 Issue | PO 分類後套用 |
| `question` | 問題詢問類 Issue | PO 分類後套用 |
| `triaged` | PO 已完成審查 | PO 審查通過後套用 |
| `backlog-linked` | 已建立對應 Backlog Issue | PO 建立 Backlog Issue 後套用 |

**Backlog Issue labels（PO 審查後建立的結構化 User Story Issue）**

| Label | 語意 | 設置時機 |
|-------|------|---------|
| `type: backlog-item` | 識別為結構化 Story，區別於原始 Issue | 建立時套用 |
| `status: backlog` | 尚未排入 Sprint 的待選 Story | 建立時套用 |
| `status: in-sprint` | 已選入當前 Sprint | Sprint Planning 時由 Skill 套用 |
| `priority: must` | MoSCoW Must（本里程碑必須完成） | PO 在 Grooming 時套用 |
| `priority: should` | MoSCoW Should | PO 在 Grooming 時套用 |
| `priority: could` | MoSCoW Could | PO 在 Grooming 時套用 |
| `size: S` | T-shirt size S（估點 1） | Architect 在 Planning 時套用 |
| `size: M` | T-shirt size M | Architect 在 Planning 時套用 |
| `size: L` | T-shirt size L | Architect 在 Planning 時套用 |

#### Milestone 設計

每個 Sprint 建立對應的 GitHub Milestone：

```bash
# 建立 Sprint N Milestone
gh milestone create "Sprint N" --due-date "YYYY-MM-DD"

# Sprint Planning：將選入的 Issues 關聯至 Milestone
gh issue edit <number> --milestone "Sprint N"

# 查詢 Sprint N 的 Backlog
gh issue list --milestone "Sprint N" --state open

# Story 完成
gh issue close <number>
```

#### 優點

- 與 Issue #46 原始設計完全一致，架構意圖清晰
- 消除雙向同步問題：GitHub Issues 是唯一狀態記錄，close Issue 即等於 done，無需維持兩套系統
- `gh issue list` 提供豐富的過濾能力（label、milestone、state、assignee），Sprint Planning 可直接使用
- Story 的生命週期（open → in-sprint → closed）完全由 GitHub 原生機制追蹤，無需額外工具
- backlog-intake Skill 的職責從「轉化 Issue 為 .md 格式」簡化為「為 Issue 套用 label + 填補 Story 細節」，實作更輕薄
- Issue number 成為 Story 的唯一識別碼，消除 US-NN 與 Issue number 雙套識別的認知負擔

#### 缺點

- 需改動三個 SKILL.md（backlog-intake、sprint-planning、backlog-management）
- RICE 分數、MoSCoW 標籤目前儲存在 PRODUCT_BACKLOG.md 的表格格式中；遷移後需改以 Issue label（MoSCoW）+ Issue body（RICE 細節）儲存，格式豐富度略降
- GitHub Issues 的 body 欄位為自由文字，Acceptance Criteria 的結構化程度依賴 Issue template 規範，若 template 不完整則品質參差
- 離線瀏覽需要 gh CLI 或 GitHub Web UI，無法在純檔案系統環境中查看完整 Backlog
- 現有 Backlog 的已排程 Stories（US-01 至 US-65+）需要遷移至 GitHub Issues 或建立映射關係

#### 受影響的 SKILL.md 清單

| SKILL.md | 改動性質 | 影響範圍 |
|----------|---------|---------|
| `skills/backlog-intake/SKILL.md` | 重大改寫：移除寫入 PRODUCT_BACKLOG.md 的步驟，改為為 Issue 套用 label + 填補 Story template | 核心流程（§3 解析流程、§5 輸出格式規範）全部重寫 |
| `skills/sprint-planning/SKILL.md` | 中度修改：PO subagent 的 Story 來源從讀取 .md 改為 `gh issue list` | §2 Checklist Step 4、§6 派遣順序 Step 1 與 Step 4 |
| `skills/backlog-management/SKILL.md` | 中度修改：Product Discovery 與 Backlog Grooming 的產出從 .md 改為 GitHub Issues | §2 Product Discovery、§3 Backlog Grooming、§6 產出文件 |

#### 回溯相容策略

現有 US-01 至 US-65+ 的歷史 Stories 已歸檔於 `docs/prd/BACKLOG_DONE.md`（已完成）或 `docs/prd/PRODUCT_BACKLOG.md`（未完成）。遷移策略如下：

| Story 狀態 | 遷移方式 |
|-----------|---------|
| 已完成 Stories（US-01 至 US-65） | 保留在 BACKLOG_DONE.md 作為歷史記錄，不需遷移至 GitHub Issues |
| 未完成 / 未排程 Stories（若有） | 於遷移 Sprint 開立對應 GitHub Issues，套用 `status: backlog` label |
| PRODUCT_BACKLOG.md | 降級為唯讀歷史快照，加入 deprecation 標頭，停止寫入 |

#### 遷移成本

- 3 個 SKILL.md 的修改（預估 3 個 S-size Stories）
- ADR-009 的 Decision Challenge：backlog-intake Skill 需重新評估其核心職責（from 入庫到 .md，to 為 Issue 套用 label + 填補 Story 細節）
- Label 初始化（`gh label create`）：約 8-10 個新 label
- Milestone 建立流程需納入 Sprint Planning SKILL.md 的前置步驟

### Option C：混合模式（Issues 為 source of truth + .md 為自動化快照）

GitHub Issues 作為 source of truth，PRODUCT_BACKLOG.md 由自動化腳本從 Issues 生成（唯讀快照），兩者並存但 .md 只讀不寫。

#### 架構設計

```
GitHub Issues ← Source of Truth
    │
    │ gh issue list（自動化腳本，定時或觸發執行）
    ▼
PRODUCT_BACKLOG.md（唯讀快照，自動生成）
    │
    │ sprint-planning 讀取（仍可用 .md，向後相容）
    ▼
Sprint Backlog
```

#### 優點

- GitHub Issues 成為真正的 source of truth，符合 Issue #46 設計意圖
- PRODUCT_BACKLOG.md 快照保留離線可讀性與豐富格式（可由腳本重新生成）
- 現有 sprint-planning / backlog-management 讀取 .md 的流程不需立即改動（快照持續更新即可相容）

#### 缺點

- 引入額外的「快照生成腳本」，增加維護複雜度與失敗點（腳本失敗 → 快照過時 → sprint-planning 讀取錯誤資料）
- 若 sprint-planning 仍讀取 .md 快照，等同於 sprint-planning 是讀「GitHub Issues 的間接映射」而非直接來源，source of truth 的清晰度被稀釋
- 快照的時間一致性問題：Issues 更新後，快照需要多久才反映新狀態？若 Sprint Planning 在快照更新前執行，可能基於過時資料選取 Stories
- 快照腳本本身的格式規範需另行定義，等同於引入一個新的技術元件
- 違反 YAGNI 原則：快照腳本是為了「離線可讀性」這一個需求而引入的間接層，而這個需求在 Shikigami 的核心使用情境（Claude Code + gh CLI 環境）中優先級較低

#### 遷移成本

- 快照生成腳本的設計與實作（新增元件）
- SKILL.md 的改動量介於 Option A 與 Option B 之間（backlog-intake 需改動，sprint-planning 可暫時不改）

| ADR-009 相容性 | 完全相容 | 需更新 backlog-intake 職責 | 部分相容 |

## 決策

**採用 Option B：GitHub Issues 為唯一 Backlog source of truth（Issue #46 原始設計）。**

理由如下：

### 1. 設計一致性（最關鍵理由）

Issue #46 的「Backlog = GitHub Issues」是整個自動化排程框架的核心架構哲學。四條流程（需求入庫 → Sprint Planning → 排程衝刺 → 程式碼入庫）的設計都預設 Issues 是 Backlog 的原生容器。ADR-009 在實作方向上的偏離雖然有其過渡期的合理性，但隨著框架成熟，這個偏離會累積成更大的架構技術債。

### 2. 消除根本性的雙向同步問題

Option A 在每次 Story 狀態轉換時都需要維持 GitHub Issues 與 PRODUCT_BACKLOG.md 兩個系統的一致性。這不是可以透過工具解決的偶發問題，而是雙系統架構的結構性缺陷——任何時間點都可能出現兩系統狀態不一致的情況，且這種不一致會隨 Sprint 數量線性積累。

### 3. Option C 引入的複雜度超過其解決的問題

「離線可讀性」是 Option C 快照層存在的主要理由。然而 Shikigami 的核心使用情境（Claude Code + gh CLI + GitHub 認證的開發環境）並不是一個頻繁需要離線查看 Backlog 的情境。快照層引入的維護複雜度（時間一致性、腳本失敗處理、快照格式定義）遠超過離線可讀性的使用價值。

### 4. 遷移成本可控且有邊界

Option B 的 SKILL.md 修改範圍明確（3 個 Skill），影響可預見。現有的歷史 Stories 不需要回溯遷移——已完成的 Stories 保留在 BACKLOG_DONE.md 作為歷史記錄，PRODUCT_BACKLOG.md 降級為唯讀快照並加入 deprecation 標頭，遷移邊界清晰。

## 設計細節

本節記錄決策通過 QA Decision Challenge（ACCEPT-WITH-CONDITIONS）後整合的設計細節，解決原始提案中的開放問題並補充實作規範。

### 兩層 Issue 設計

Issue 體系採用兩層結構，分離使用者原始需求與 PO 結構化 Story：

**原始 Issue（如 #60）**：使用者開立，包含原始需求描述、討論與背景。體現使用者需求的原始意圖。

**Backlog Issue（如 #71）**：PO 審查後建立的結構化 User Story。body 中寫明「來源：#60」，GitHub 自動在 #60 的 timeline 顯示「#71 mentioned this issue」，形成可追溯的連結。一個原始 Issue 可以拆分成多個 Backlog Issues。

兩層設計的關鍵約定：
- Backlog Issue 的 body 必須包含「來源：#原始Issue編號」（冪等性保護依賴此欄位）
- Backlog Issue 套用 `type: backlog-item` label 以區別於原始 Issue
- GitHub 的交叉引用機制自動維護兩層 Issue 的視覺連結，無需額外工具

### PO 審查閘門

**建立 Backlog Issue = PO 審查通過**。不建立 = 拒絕，PO 在原始 Issue 回覆拒絕原因並套用 `triaged` label。

PO 審查包含三項判斷：
1. **合理性判斷**：需求是否符合產品方向與里程碑目標
2. **分類**：`feature-request` / `bug` / `question`
3. **拒絕機制**：若拒絕，在原始 Issue 回覆說明理由，並套用 `triaged` label（不套用 `backlog-linked`）

### RICE 分數儲存方案

RICE 分數儲存於 Backlog Issue body 的固定 template section，使用可機器解析的表格格式：

```markdown
## RICE 評分

| 因子 | 分數 | 說明 |
|------|------|------|
| Reach | 8 | ... |
| Impact | 3 | ... |
| Confidence | 0.8 | ... |
| Effort | 1 | ... |
| **RICE Score** | **19.2** | R×I×C/E |
```

PO subagent 用正則表達式提取「**RICE Score** | **\<數字\>**」行的數值，不依賴 LLM 解析，確保可靠性與效能。

此設計解決了 QA 開放問題 1（RICE 分數儲存位置）。

### Backlog 排序機制

排序不持久化，由 PO subagent 在 Sprint Planning 查詢時即時計算，步驟如下：

1. 查詢 Backlog Issues：
   ```bash
   gh issue list --label "type: backlog-item" --label "status: backlog" --state open \
     --json number,title,body,labels --limit 200
   ```
2. 從 body 以正則表達式提取 RICE Score 數值
3. 排序規則：先依 MoSCoW tier（must > should > could）降序，同 tier 內再依 RICE Score 降序
4. 從排序結果頂部選取適合本 Sprint 的 Stories

此設計解決了 QA 開放問題 2（Backlog 排序問題），避免引入持久化排序欄位的維護負擔。

### 錯誤恢復策略

GitHub API 操作失敗時的冪等性保護機制：

| 失敗情境 | 恢復機制 |
|---------|---------|
| Label 操作進行到一半 crash | 下次執行前的 Pre-flight 掃描偵測不一致的 label 狀態，自動修復至目標狀態 |
| Backlog Issue 建立成功，但標記原始 Issue 失敗 | 下次執行時，透過掃描 Backlog Issues 的 body「來源：#N」欄位，偵測已存在的對應關係，跳過重複建立 |
| Sprint Planning 改 milestone 進行到一半失敗 | Planning 開始前的 Pre-flight 掃描偵測 milestone/label 狀態不一致的 Issues，自動修復後再繼續 |

Pre-flight 掃描為所有 Skill 執行前的必要步驟，確保 GitHub Issues 狀態在操作開始前處於已知一致狀態。

## 決策影響

### 對 ADR-009 的影響

## QA Decision Challenge 結果

**結果**：ACCEPT-WITH-CONDITIONS

QA 提出五個先決條件，全部於本次 ADR 更新中解決：

| 條件 | 說明 | 解決方式 |
|------|------|---------|
| 1. RICE 儲存方案明確化 | 原提案未定義 RICE 分數在 GitHub Issues 體系中的儲存格式 | 採用 Issue body 固定 template section，正則提取 RICE Score 數值（見「設計細節」§ RICE 分數儲存方案） |
| 2. 排序機制明確化 | 原提案未定義取代 PRODUCT_BACKLOG.md 手動排序的方案 | 採用 Sprint Planning 即時計算：MoSCoW tier 優先，同 tier 內 RICE 降序（見「設計細節」§ Backlog 排序機制） |
| 3. 原子性交付約束 | SKILL.md 修改與 PRODUCT_BACKLOG.md 降級需同步完成，避免中間狀態 | 實作路線圖步驟 2-5 合併為單一 Sprint 原子性交付，PRODUCT_BACKLOG.md 的 DEPRECATED 標頭不得先於三個 SKILL.md 修改完成 |
| 4. 錯誤恢復策略 | 原提案未定義 GitHub API 操作失敗時的恢復機制 | 定義三種失敗情境的 Pre-flight 掃描與冪等性恢復策略（見「設計細節」§ 錯誤恢復策略） |
| 5. 兩層 Issue 設計明確化 | 原始 Issue 與 Backlog Issue 的關係、label 分層需明確定義 | 定義兩層 label 集合與 PO 審查閘門，body「來源：#N」欄位作為冪等性保護依據（見「設計細節」§ 兩層 Issue 設計） |

## 實作路線圖

**原子性交付約束**：步驟 2-5 必須在同一 Sprint 內完成，作為單一原子性交付。PRODUCT_BACKLOG.md 的 DEPRECATED 標頭（步驟 2）不得先於三個 SKILL.md 修改（步驟 3-5）完成——即若 SKILL.md 修改尚未完成，DEPRECATED 標頭不應先行加入，以避免 Skills 在無正確來源讀取的狀態下執行。

| 順序 | Story | 說明 | 原子性 |
|------|-------|------|--------|
| 1 | GitHub Labels 初始化 | 建立 ADR-010 定義的所有 label（兩層 label 集合），並更新 Pre-flight 檢查 | 可獨立執行 |
| 2 | PRODUCT_BACKLOG.md 降級 | 加入 deprecation 標頭，凍結寫入 | 步驟 2-5 原子 |
| 3 | backlog-intake SKILL.md 改寫 | 輸出目標從 .md 改為 Issue label + body template；加入 PO 審查閘門、兩層 Issue 建立流程 | 步驟 2-5 原子 |
| 4 | sprint-planning SKILL.md 修改 | PO Story 選取來源改為 `gh issue list`；加入即時排序計算邏輯 | 步驟 2-5 原子 |
| 5 | backlog-management SKILL.md 修改 | Grooming 流程改為操作 GitHub Issues；加入 Pre-flight 錯誤恢復掃描 | 步驟 2-5 原子 |
| 6 | ADR-009 標注更新 | 在格式契約決策域加入「Superseded by ADR-010」標注 | 可獨立執行 |

## 風險評估

| 風險 | 可能性 | 影響 | 緩解策略 |
|------|--------|------|---------|
| Issue body 格式品質不一（Acceptance Criteria 不完整） | 中 | 中 | 建立 GitHub Issue Template，明確要求 User Story + AC + RICE 欄位 |
| Milestone 管理遺漏（Story 未關聯至 Sprint Milestone） | 低 | 中 | sprint-planning SKILL.md 的 Pre-flight 驗證 Milestone 是否存在 |
| `gh issue list` 的 50-issue 預設上限在大型 Backlog 中不足 | 低 | 低 | 明確在 SKILL.md 中指定 `--limit 200`（或適當上限） |
| 歷史 Story ID（US-NN）與 GitHub Issue number 的映射關係遺失 | 低 | 低 | PRODUCT_BACKLOG.md 保留為唯讀快照，歷史映射關係不會遺失 |
| ADR-009 的 backlog-intake-done 冪等性機制與新 label 體系的相容性 | 低 | 低 | `backlog-intake-done` label 繼續沿用，與新 label 體系並存，不衝突 |
| GitHub API 操作失敗導致 Issue 狀態不一致 | 低 | 中 | Pre-flight 掃描 + 冪等性保護機制（見「設計細節」§ 錯誤恢復策略） |
| RICE 正則提取失敗（body 格式不符） | 低 | 低 | Backlog Issue template 強制包含 RICE 欄位；提取失敗時以 RICE Score = 0 處理並記錄警告 |
