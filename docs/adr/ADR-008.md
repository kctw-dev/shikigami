# ADR-008：OpenCode 平台整合策略

**狀態**：Accepted
**日期**：2026-03-03
**決策者**：Architect
**挑戰者**：QA Engineer
**關聯 Issue**：#3（支援 OpenCode / Codex 平台安裝）
**關聯 Story**：US-47（Sprint 27）、US-46（Sprint 26，Phase 1 執行）
**前置文件**：[OPENCODE_POC.md](../km/OPENCODE_POC.md)（Phase 1 完成記錄）

---

## 背景

Shikigami 框架目前僅在 Claude Code 平台上完整驗證。Issue #3 請求支援 OpenCode 平台安裝，使外部使用者（非 Claude Code 訂閱者）能在 OpenCode 環境中運行 Shikigami 完整工作流，對應 M5 里程碑條件 (a) 外部使用者觸及。

**Phase 1 調查結論（US-46，Sprint 26）**：

OPENCODE_POC.md 的 Go/No-Go 決策為 **Go**。靜態分析顯示 OpenCode 在三個核心機制上具備高相容性（評分 4/5，三個候選平台中最高）：

| 核心機制 | 相容性評估 |
|---------|------------|
| SKILL.md 等效載入 | 高度相容（目錄結構 symlink 即可適配） |
| Task tool subagent 派遣 | 高度相似，移植成本低 |
| bash / gh CLI 權限 | 完全支援，per-agent 隔離亦相容 |

Phase 1 實際執行（US-46）已完成目錄適配（`.opencode/skills` symlink）、AGENTS.md 建立，並識別出 7 項 Claude Code 特有 API 殘留項（R-1 至 R-7），均為說明性或有降級路徑的功能性殘留，不阻斷 Phase 1 DoD。

**subagent 設定檔路徑策略的必要性**：Phase 1 靜態驗證後，Phase 2 需要建立五個 OpenCode 自訂 subagent 設定檔（PO / Architect / QA / Developer / SM）。設定檔的存放路徑與格式需在 ADR 層面確定，確保 Phase 2 執行（US-48）有一致的規範可循。

---

## 決策問題

Shikigami 整合 OpenCode 平台時，應採用何種技術策略，使現有的 SKILL.md 框架、五角色 subagent 模型，以及 Claude Code 平台上的完整工作流能在 OpenCode 上以最低成本可靠運作？具體子問題包括：

1. 目錄結構應如何適配（symlink vs. 複製 vs. 重建）？
2. SKILL.md 中 Claude Code 特有殘留項（R-1 至 R-7）應如何處置？
3. OpenCode subagent 設定檔應存放於何處、採用何種格式？
4. 主框架入口（AGENTS.md）應如何定義？

---

## 選項分析

### 選項 A：Symlink 適配策略（採用）

以 symlink 將 `.opencode/skills` 指向現有 `skills/` 目錄，實現零複製的路徑適配；subagent 設定檔統一存放於 `.opencode/agents/` 目錄；SKILL.md 殘留項採雙平台標注方式處置；AGENTS.md 作為 OpenCode 專屬框架入口。

**優點：**
- 零重複內容：`skills/` 目錄維持單一來源，symlink 使兩個平台共用同一份 SKILL.md，不存在內容漂移問題
- 成本最低：Phase 1 已驗證此方案可行，主要工作為 symlink 建立（已完成）
- 維護簡單：更新 `skills/` 內容即可同步至兩個平台
- 雙平台標注保留 Claude Code 現有用戶的使用體驗

**缺點：**
- Symlink 在 git 追蹤上需要注意（需確認 symlink 被 git 正確追蹤，而非追蹤 symlink 目標的內容）
- 雙平台標注增加 SKILL.md 文件長度，可讀性略有下降

**風險：**
- 若未來 OpenCode 更改 `.opencode/skills/` 掃描行為，symlink 適配可能失效（低機率，有監控機制緩解）

---

### 選項 B：目錄複製策略

將 `skills/` 目錄完整複製為 `.opencode/skills/`，維護兩份獨立的 SKILL.md 集合。

**優點：**
- 兩個平台完全獨立，互不影響
- OpenCode 專屬的 SKILL.md 可做更深度的客製化

**缺點：**
- 內容重複：任何 SKILL.md 修改都需同步到兩個目錄，維護成本倍增
- 內容漂移風險高：兩份 SKILL.md 的差異隨時間擴大，最終形成不可維護的分支

**風險：**
- 維護負擔在 21 個 SKILL.md、21 個技能的規模下不可持續

---

### 選項 C：重建策略（OpenCode-first）

重新設計 Shikigami 的目錄結構，以 OpenCode 為主要平台，Claude Code 降為次要平台。

**優點：**
- 針對 OpenCode 最佳化

**缺點：**
- 破壞現有 Claude Code 平台的完整功能
- 遷移成本最高，等同於重寫框架
- 與 M5 目標衝突（M5 要求擴展至 OpenCode，非取代 Claude Code）

---

## 決策

**採用選項 A（Symlink 適配策略），並以以下具體技術策略實作 OpenCode 平台整合。**

### 決策一：目錄結構策略

**Symlink 適配**為唯一正式支援的目錄整合方式。結構定義如下：

```
repo 根目錄/
├── skills/                        ← 唯一來源（Claude Code 主平台）
│   ├── sprint-planning/SKILL.md
│   ├── sprint-execution/SKILL.md
│   └── ...（共 21 個技能）
├── .opencode/                     ← OpenCode 平台適配目錄
│   ├── skills -> ../skills        ← symlink（Phase 1 已建立，git 追蹤中）
│   └── agents/                   ← subagent 設定檔目錄（Phase 2 建立）
│       ├── developer.md
│       ├── architect.md
│       ├── qa-engineer.md
│       ├── product-owner.md
│       └── scrum-master.md
└── AGENTS.md                      ← OpenCode 框架入口（Phase 1 已建立）
```

**不允許**以目錄複製或重建方式維護兩份 SKILL.md，以防止內容漂移。

### 決策二：SKILL.md 殘留項處置策略（R-1 至 R-7）

Phase 1 識別的 7 項 Claude Code 特有 API 殘留項，依以下規則處置：

| 殘留項類型 | 處置方式 | 執行時程 |
|-----------|---------|---------|
| 說明性殘留（R-1、R-2、R-4、R-5、R-6、R-7，共 6 項） | 雙平台標注（dual-platform annotation）：保留原 Claude Code 語法，補充 OpenCode 對應說明 | Phase 2（US-48） |
| 功能性殘留（R-3：`~/.claude/projects/` 路徑） | 雙平台標注：保留原路徑說明，補充 OpenCode session 資料路徑（待 Phase 2 調查確認後填入） | Phase 2（US-48） |

**雙平台標注格式規範**：

```markdown
<!-- Claude Code -->
claude -p "/sprint-planning"

<!-- OpenCode -->
opencode <skill-name>   ← 待 Phase 2 確認後填入正確語法
```

**不允許**在不提供替代說明的情況下直接刪除 Claude Code 語法，以防止現有用戶體驗退化。

### 決策三：Subagent 設定檔路徑策略與格式規範

**路徑規範**：

OpenCode 自訂 subagent 設定檔統一存放於 `.opencode/agents/` 目錄，每個角色一個 Markdown 文件：

```
.opencode/agents/
├── developer.md        ← Developer 角色 prompt
├── architect.md        ← Architect 角色 prompt
├── qa-engineer.md      ← QA Engineer 角色 prompt
├── product-owner.md    ← PO 角色 prompt
└── scrum-master.md     ← Scrum Master 角色 prompt
```

**格式規範**：

每個 subagent 設定檔採用 YAML frontmatter + Markdown 格式：

```yaml
---
name: <角色英文名稱>
description: <角色職責一句話說明>
---

<角色 system prompt 正文（Markdown 格式）>
```

**格式選型依據**：

- OpenCode subagent 設定採用 `name` + `description` frontmatter（與 SKILL.md 格式一致），降低格式認知切換成本
- Markdown 格式與現有 `skills/*/SKILL.md` 保持一致，符合框架一致性原則
- YAML frontmatter 為 OpenCode Agents 文件定義的必填欄位格式（參考：https://opencode.ai/docs/agents/）

**派遣方式**：

OpenCode subagent 派遣透過原生 Task tool 實現，與 Claude Code 的 Task tool 設計相似。主框架（AGENTS.md / SKILL.md）的 Scrum Master 角色透過 Task tool 按需派遣五個角色：

```
Task tool 呼叫模式：
  → 讀取 .opencode/agents/<role>.md 作為 subagent system prompt
  → 以 Task tool 傳入任務描述（prompt 欄位）
  → 接收 subagent 回傳結果
```

**已知待確認項（Phase 2 範疇）**：

Task tool 的具體參數欄位命名（`description`、`prompt` 等）需在 Phase 2 實機 POC 中對照 OpenCode 文件確認，可能與 Claude Code Task tool 存在命名差異。

### 決策四：AGENTS.md 作為 OpenCode 平台入口

`AGENTS.md`（repo 根目錄）作為 OpenCode 的框架入口，功能對應 Claude Code 環境的 `CLAUDE.md`。AGENTS.md 定義：

- 框架概覽與角色定義
- OpenCode Skills 載入路徑說明（`.opencode/skills/*/SKILL.md`）
- OpenCode 特有設定說明（Skills 調用方式、subagent 派遣方式）
- 已知相容性注意事項（Phase 1 識別的遺留調查項）

## 影響

### 正面影響

| 影響 | 說明 |
|------|------|
| 外部用戶觸及擴展 | OpenCode 的 model-agnostic 設計使非 Claude Code 訂閱者可使用 Shikigami，直接支援 M5 里程碑條件 (a) |
| 零維護重複 | Symlink 策略確保 `skills/` 唯一來源，21 個 SKILL.md 的更新自動同步至 OpenCode 平台 |
| 最低遷移成本 | Phase 1 已完成核心適配，Phase 2 的主要工作為 subagent 設定檔建立與殘留項標注 |
| 框架一致性 | subagent 設定檔格式（YAML frontmatter + Markdown）與 SKILL.md 格式保持一致，降低認知負擔 |
| 可逆決策 | Symlink 適配不修改 `skills/` 核心內容，若 OpenCode 整合失敗可無損回退 |

### 負面影響與緩解策略

| 負面影響 | 風險等級 | 緩解策略 |
|---------|---------|---------|
| Task tool 參數格式差異（B-3）：OpenCode Task tool 與 Claude Code 參數欄位命名可能不同，導致 subagent 派遣失敗 | 低至中 | Phase 2 US-48 AC4 靜態驗證步驟：對照 OpenCode 官方文件逐一確認 `description`、`prompt` 等欄位命名；建立參數對應表記錄於 OPENCODE_POC.md §9 |
| SessionStart hook 等效性未確認（B-2）：Shikigami 依賴 Claude Code `SessionStart` hook 觸發框架初始化，OpenCode 的等效機制尚未驗證 | 中 | Phase 2 US-48 AC1 調查步驟：審查 OpenCode session 生命週期文件，識別等效 hook 或替代初始化路徑；若無等效機制，採用「按需初始化」降級策略（使用者首次呼叫 Skill 時觸發） |
| 模型行為差異（B-1）：OpenCode model-agnostic 設計使非 Claude 模型對相同 SKILL.md prompt 的執行品質可能不一致 | 中 | AGENTS.md 中明確建議使用者選擇 Claude 系列模型以獲得最佳結果；安裝指南（Phase 3，docs/INSTALL_OPENCODE.md）涵蓋模型選擇建議；SKILL.md prompt 工程審查（Phase 2 AC3 標注階段）識別高模型敏感度的描述並調整 |
| Symlink git 追蹤風險：若 git 設定或 CI/CD 環境不正確處理 symlink，`.opencode/skills` 可能被追蹤為損壞的 symlink | 低 | Phase 1 已驗證 symlink 在 git 中正確追蹤（git ls-files 可見）；在 repo README 中記錄 symlink 存在，提醒 Windows 用戶使用 `git config core.symlinks true` |
| 雙平台標注增加 SKILL.md 長度：R-1 至 R-7 的雙平台標注可能使 `sprint-planning/SKILL.md` 的可讀性下降 | 低 | 標注採用 HTML 注釋格式（`<!-- Claude Code --> ... <!-- OpenCode --> ...`），在 Markdown 渲染時隱藏，不影響主流閱讀體驗；僅在原始碼層面可見 |
| OpenCode 版本更新風險：OpenCode 為活躍開發項目，`.opencode/` 目錄規範或 Task tool API 可能在版本更新中變更 | 低 | OPENCODE_POC.md §7 版本資訊表提供版本追蹤機制；建議在每次 OpenCode 主版本更新後執行相容性審查（可作為定期維護任務） |

## Decision Challenge（QA Engineer）

**挑戰**：ADR-008 的 subagent 設定檔格式規範（YAML frontmatter + Markdown）目前基於 Phase 1 靜態分析，尚未在實機 OpenCode 環境中驗證。若 OpenCode 的實際 Agents 解析行為與文件描述不符（例如需要額外的必填欄位，或 frontmatter 格式有嚴格版本要求），Phase 2 的移植工作可能需要回頭修訂 ADR-008 定義的格式規範。

**反駁**：此挑戰正確識別了靜態分析的局限性。以下三點說明為何 ADR-008 的格式規範在此不確定性下仍屬合理的架構決策：

第一，格式規範的「核心不變量」（`name` + `description` frontmatter + Markdown 正文）基於 OpenCode 官方 Skills 文件（https://opencode.ai/docs/skills/）的明確定義，與 SKILL.md 的既有格式高度一致，此部分的不確定性最低。

第二，ADR-008 明確標注「已知待確認項（Phase 2 範疇）」，將 Task tool 參數欄位命名差異的確認工作留給 US-48 AC4 靜態驗證步驟，而非在 ADR 中做出無法驗證的假設。這是責任歸屬的正確分配。

第三，若 Phase 2 實機驗證發現格式規範需調整，ADR-008 的修訂成本極低（格式規範是文件決策，非代碼決策），且 Stakeholder Review 修訂記錄機制允許在不推翻整體架構方向的前提下局部更新格式規範。

**結論**：接受此挑戰作為有效的品質監控提醒。US-48 AC4 的靜態驗證結論必須明確記錄格式規範的實際相容性，並在發現偏差時觸發 ADR-008 的 Stakeholder Review 修訂流程。
