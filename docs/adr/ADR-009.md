# ADR-009：Backlog Intake 自動化技術決策

**狀態**：Accepted
**日期**：2026-03-03
**決策者**：Architect
**挑戰者**：QA Engineer
**關聯 Issue**：#46（shikigami:backlog-intake — PO Backlog Intake cron + 需求入庫自動化）
**關聯 Story**：US-63（Sprint 33）
**前置 ADR**：ADR-005（Schedule Skill 技術決策）、ADR-006（Issue 內容提示注入防護）

---

## 背景

Issue #46 子 Story #4 要求實作 `shikigami:backlog-intake` Skill，讓 Product Owner 能以 cron 驅動的方式自動將 GitHub Issues 轉化為 Product Backlog 的結構化 User Story 格式，在 Sprint 週期之間維持 Backlog 的即時更新，無需人工介入。

此 Skill 涉及五個技術決策域，其中決策域四（cron 認證策略）直接繼承 ADR-005 的決策，決策域三（injection 防護邊界）補充說明與 ADR-006 的繼承關係。

---

## 決策域一：輸入來源模型

### 決策問題

`shikigami:backlog-intake` 應從哪些來源讀取新需求，並以什麼判斷條件決定哪些 Issue 需要入庫？

### 選項分析

#### 選項 A：GitHub Issues 作為唯一輸入來源（採用）

以 `gh issue list` 讀取 GitHub Issues，搭配 label 過濾（`backlog-intake` 或無 sprint-replied label）識別待入庫 Issues。

- 優點：與 ADR-006 的 Issue 快掃流程共用相同的資料來源，維護一致；`gh` CLI 已在 Pre-flight 中驗證可用性；Issue 的結構化 metadata（title、body、labels、number）提供足夠的格式轉換基礎
- 缺點：依賴 GitHub Issues 作為唯一需求來源，若團隊使用其他 issue tracker 則無法適用
- 風險：GitHub API rate limit 在高頻排程下可能觸發限制（`gh issue list` 預設使用 OAuth 認證，rate limit 為每小時 5000 次請求，backlog-intake 的實際請求量遠低於此上限）

#### 選項 B：多來源輸入（GitHub Issues + Markdown 檔案 + 外部 Webhook）

支援多種需求輸入來源，以統一的輸入適配器模型處理不同格式。

- 優點：擴展性高
- 缺點：實作複雜度超出 MVP 需求；外部 webhook 引入額外的認證與安全考量；違反 YAGNI 原則
- 風險：多來源適配層的抽象設計過早，Shikigami 目前的使用情境已由 GitHub Issues 完整覆蓋

### 決策

**採用選項 A（GitHub Issues 作為唯一輸入來源）。**

理由：

1. **一致性**：backlog-intake 與 sprint-execution §3 Issue 快掃使用相同的 `gh issue list` 資料來源，降低認知負擔與維護成本
2. **MVP 原則**：GitHub Issues 完整覆蓋 Shikigami 的目標使用情境，引入多來源適配器是 YAGNI 的過早設計
3. **去重機制基礎**：Issue number 作為天然的唯一識別碼，為決策域五的冪等性保護提供可靠基礎

**輸入過濾條件**：

| 條件 | 說明 |
|------|------|
| label 過濾 | 讀取帶有 `backlog-intake` label 的 Issues（未設定此 label 的 Issues 不入庫） |
| 狀態過濾 | 僅讀取 `open` 狀態的 Issues |
| 去重保護 | Issues 帶有 `backlog-intake-done` label 者視為已入庫，跳過（決策域五詳述） |

## 決策域二：格式契約

### 決策問題

GitHub Issue 轉化為 Product Backlog User Story 時，應採用什麼輸出格式標準？輸出文件應寫入哪個位置？

### 選項分析

#### 選項 A：寫入 PRODUCT_BACKLOG.md 標準格式（採用）

遵循既有 `docs/prd/PRODUCT_BACKLOG.md` 的 User Story 格式，以 AI 解析 Issue 內容後生成符合框架規範的 Story 條目，append 至 Backlog 底部的未排程區段。

- 優點：與既有 Backlog 格式完全一致，PO 無需額外格式轉換；複用現有 PRODUCT_BACKLOG.md 的 Story ID 命名慣例（`US-NN` 格式）
- 缺點：若 Issue 品質低（描述不充分），AI 生成的 Story 條目可能需要人工補全
- 風險：多個 backlog-intake 執行並行時可能造成 Story ID 號碼衝突（由決策域五的冪等性機制處理）

#### 選項 B：獨立的 INTAKE_QUEUE.md 暫存區

新建 `docs/prd/INTAKE_QUEUE.md` 作為入庫暫存，PO 審查後再手動合併至 PRODUCT_BACKLOG.md。

- 優點：有 PO 人工審查閘門
- 缺點：增加 PO 手動工作量，與「無需人工介入」的 Story 設計目標衝突；雙檔案維護增加複雜度
- 風險：INTAKE_QUEUE 與 PRODUCT_BACKLOG 的同步規則若未明確定義，容易產生遺漏

### 決策

**採用選項 A（寫入 PRODUCT_BACKLOG.md 標準格式）。**

理由：

1. **格式一致性**：直接寫入 PRODUCT_BACKLOG.md 確保 Backlog 始終是唯一真相來源，符合 DRY 原則
2. **自動化目標**：Story 設計明確要求「無需人工 PO 介入」，暫存閘門違反此設計目標
3. **可追溯性**：每個入庫的 Story 在 `docs/prd/PRODUCT_BACKLOG.md` 中記錄來源 Issue 編號，確保 GitHub Issue 與 Backlog Story 的雙向可追溯

**輸出格式規範**：

```markdown
| US-NN | <Story 標題（來自 Issue title）> | — | — | — | 未排程 |
```

Story 詳細內容以 GitHub Issue URL 作為來源引用，在 Backlog 的 Story 詳細區段補充：

```markdown
**來源**：GitHub Issue #<issue-number>（<issue-url>）
**入庫時間**：<YYYY-MM-DD>
**入庫狀態**：待 PO 精化
```

## 決策域三：Injection 防護邊界

### 決策問題

backlog-intake Skill 在處理 GitHub Issue 內容（title、body）時，如何防止 LLM Prompt Injection 攻擊？

### 與 ADR-006 的繼承關係

**繼承範圍**：backlog-intake 繼承 ADR-006 定義的 **Prompt Injection Isolation Rule（完整兩條規則）**：

| 規則 | 內容 | 繼承方式 |
|------|------|----------|
| 規則 1 — XML 資料隔離標記 | Issue title 與 body 以 `<issue_title>` / `<issue_body>` XML 標記包裹，與系統指令在語義上分離 | 完整繼承，相同標記格式 |
| 規則 2 — 角色限制宣告 | AI subagent 的系統指令中包含明確角色邊界宣告，限制操作範圍為「轉化 Issue 為 User Story 格式」 | 繼承後擴充：角色限制宣告改為限制 backlog-intake 的操作邊界 |

**補充邊界（backlog-intake 特有）**：

backlog-intake 的操作邊界比 sprint-execution §3（起草 Issue 回覆）更廣——它要寫入 PRODUCT_BACKLOG.md。因此在 ADR-006 雙重緩解的基礎上，增加以下補充邊界：

| 補充規則 | 說明 |
|---------|------|
| 輸出格式強制限制 | AI subagent 的輸出必須限定為預定義的 Markdown 表格格式（US-NN + 標題 + 來源），拒絕任何超出此格式的輸出 |
| 寫入位置限制 | 僅允許 append 至 PRODUCT_BACKLOG.md 的「未排程」區段，不得修改 Backlog 的其他部分 |
| Issue 內容與 Story 格式嚴格分離 | Issue title 僅用於 Story 標題生成，Issue body 僅用於輔助描述補全，不得影響 Backlog 的結構或 Story ID |

**ADR-006 不適用範圍**：

ADR-006 §「範圍限定」明確說明 `skills/sprint-execution/SKILL.md` §3 的觸發條件邏輯（label 過濾、去重）不受注入威脅，因這些步驟不將 Issue 內容傳遞給 LLM。相同邏輯適用於 backlog-intake：

- label 過濾（`backlog-intake` label 判斷）不傳遞 Issue 內容給 LLM — **不在 injection 防護範圍**
- 冪等性判斷（`backlog-intake-done` label 檢查）不傳遞 Issue 內容給 LLM — **不在 injection 防護範圍**
- Issue 內容傳遞給 AI 進行 Story 格式轉換的步驟 — **在 injection 防護範圍，適用 ADR-006 + 本 ADR 補充邊界**

## 決策域四：Cron 認證策略

### 決策問題

backlog-intake 以 cron 排程執行時，`claude` CLI 的認證方式為何？GitHub CLI（`gh`）的認證方式為何？

### 繼承 ADR-005 決策域四

**完整繼承 ADR-005 決策域四（API Key 注入策略）的所有決策**：

| 繼承項目 | 繼承內容 |
|---------|---------|
| claude CLI 認證 | 採用 OAuth 認證（`~/.claude/` 認證檔案），明確 `unset ANTHROPIC_API_KEY`；不允許 API Key 出現在排程腳本明文中 |
| Pre-flight 認證驗證 | 部署前強制執行 `preflight_check_auth()`，驗證 `claude auth status`；認證無效時阻擋部署，提示 `claude auth login` |
| crontab 環境設定 | 生成的 crontab 項目明確 `unset ANTHROPIC_API_KEY`，並設定必要的 PATH |

**繼承範圍標注**：backlog-intake 繼承 ADR-005 決策域四的**全部決策**，不做任何修改。此標注的目的是明確記錄繼承關係，避免未來維護者對 backlog-intake 的認證策略產生疑問。

**backlog-intake 額外的認證需求（gh CLI）**：

backlog-intake 還需要 `gh` CLI（GitHub CLI）進行 Issue 讀取與 label 寫入操作。gh CLI 的認證策略如下：

| 認證需求 | 策略 |
|---------|------|
| gh CLI 認證 | 依賴 `~/.config/gh/` 或 `~/.config/github-copilot/` 的持久化 OAuth token，由使用者透過 `gh auth login` 預先完成認證 |
| Pre-flight 驗證 | 部署前驗證 `gh auth status`；認證無效時阻擋部署，提示 `gh auth login` |
| 不使用 GITHUB_TOKEN 環境變數 | 與 claude CLI 的 `unset ANTHROPIC_API_KEY` 策略保持一致，避免 token 明文出現在排程腳本或 crontab 中 |

**Pre-flight 認證驗證實作（雙 CLI）**：

```bash
preflight_check_auth_backlog_intake() {
  # claude CLI: 強制 OAuth 路徑（繼承 ADR-005 決策域四）
  unset ANTHROPIC_API_KEY
  if ! claude auth status >/dev/null 2>&1; then
    echo "[FAIL] claude OAuth 認證無效或已過期"
    echo "[INFO] 請執行：claude auth login"
    return 1
  fi
  echo "[PASS] claude OAuth 認證有效"

  # gh CLI: 驗證 GitHub OAuth 認證
  if ! gh auth status >/dev/null 2>&1; then
    echo "[FAIL] gh CLI 認證無效或未設定"
    echo "[INFO] 請執行：gh auth login"
    return 1
  fi
  echo "[PASS] gh CLI 認證有效"
}
```

## 決策域五：冪等性保護

### 決策問題

backlog-intake cron 週期性執行時，如何確保同一個 GitHub Issue 不會被重複入庫至 PRODUCT_BACKLOG.md？

### 選項分析

#### 選項 A：GitHub Issue label 標記（採用）

入庫完成後，在對應的 GitHub Issue 上新增 `backlog-intake-done` label，作為「已處理」的持久化標記。下次 cron 執行時，過濾條件自動排除帶有此 label 的 Issues。

- 優點：狀態持久化於 GitHub Issues 本身，不依賴任何本地狀態檔案；即使 Shikigami 環境重建，label 標記仍然有效；與決策域一的輸入過濾條件天然整合（在 `gh issue list` 的 `--label` 過濾參數中排除已標記 Issues）
- 缺點：需要 gh CLI 的 Issue label 寫入權限；標記操作在入庫成功後執行，若標記失敗（如 API 限速）會導致下次執行重複入庫（可接受，因 Backlog 的重複 Story 有人工可識別）
- 風險：使用者若手動移除 `backlog-intake-done` label，會導致 Issue 再次被入庫。此行為應在 SKILL.md 使用說明中明確記錄（移除 label = 請求重新入庫）

#### 選項 B：本地已處理記錄檔

在本地維護一個 `.shikigami/backlog-intake-processed.txt` 檔案，記錄已處理的 Issue numbers。

- 優點：不依賴 GitHub API 寫入
- 缺點：本地狀態在環境遷移時遺失；cron 環境下的檔案路徑管理增加複雜度；本地記錄與 GitHub 實際狀態可能不同步（例如 Issue 已關閉但本地記錄仍標記為 pending）
- 風險：本地狀態檔案成為單點故障，不符合「狀態持久化」的可靠性要求

#### 選項 C：PRODUCT_BACKLOG.md 內容掃描

每次執行前掃描 PRODUCT_BACKLOG.md，檢查是否已存在來源為該 Issue 的 Story 條目。

- 優點：零額外標記操作
- 缺點：Backlog 檔案隨 Sprint 演進而修改，來源格式不一致時掃描可能誤判；掃描邏輯複雜（需 grep 特定格式的 Issue URL 引用）；不能處理 Issue 已入庫但 Story 被手動刪除的情況
- 風險：掃描準確性依賴格式嚴格性，屬於脆弱的實作

### 決策

**採用選項 A（GitHub Issue label 標記）。**

理由：

1. **狀態持久化**：`backlog-intake-done` label 持久化於 GitHub Issues，不受本地環境影響，是三個選項中可靠性最高的方案
2. **與輸入過濾天然整合**：`gh issue list --label backlog-intake` + 排除 `backlog-intake-done` 的組合在單一 API 呼叫中完成去重，不需要額外的狀態查詢步驟
3. **語意明確**：label 的存在與否對 PO 和開發者可見，提升流程透明度

**label 管理規範**：

| label | 語意 | 管理方式 |
|-------|------|---------|
| `backlog-intake` | 此 Issue 請求入庫至 Backlog | 由 Issue 建立者或 PO 手動添加，觸發 backlog-intake 處理 |
| `backlog-intake-done` | 此 Issue 已完成入庫 | 由 backlog-intake Skill 自動添加，入庫成功後執行 |

**label 初始化（Pre-flight 補充檢查）**：

首次部署時，Pre-flight 驗證 `backlog-intake` 和 `backlog-intake-done` labels 是否已在 GitHub repo 中建立：

```bash
preflight_check_labels() {
  for label in "backlog-intake" "backlog-intake-done"; do
    if ! gh label list --search "$label" --json name -q '.[].name' | grep -q "^${label}$"; then
      echo "[INFO] label '${label}' 不存在，自動建立..."
      case "$label" in
        "backlog-intake")
          gh label create "$label" --color "#0075ca" \
            --description "請求 backlog-intake Skill 入庫此 Issue" ;;
        "backlog-intake-done")
          gh label create "$label" --color "#0e8a16" \
            --description "backlog-intake Skill 已完成入庫" ;;
      esac
      echo "[PASS] label '${label}' 已建立"
    else
      echo "[PASS] label '${label}' 已存在"
    fi
  done
}
```

## 整體決策摘要

| 決策域 | 選擇 | 核心理由 |
|--------|------|----------|
| 輸入來源模型 | GitHub Issues（`gh issue list`）+ `backlog-intake` label 過濾 | 一致性、MVP 原則、Issue number 天然冪等識別碼 |
| 格式契約 | 直接寫入 PRODUCT_BACKLOG.md 標準格式 | 唯一真相來源（DRY），符合自動化目標 |
| Injection 防護邊界 | 繼承 ADR-006 Prompt Injection Isolation Rule + backlog-intake 補充邊界（輸出格式強制、寫入位置限制） | 深度防禦，擴大 ADR-006 的適用範圍 |
| Cron 認證策略 | 完整繼承 ADR-005 決策域四（OAuth）+ gh CLI OAuth 補充 | 安全性優先，API token 不出現在腳本明文 |
| 冪等性保護 | GitHub Issue label 標記（`backlog-intake-done`） | 狀態持久化於 GitHub，不依賴本地環境，可靠性最高 |

## 影響

### 對 skills/backlog-intake/SKILL.md 的影響

SKILL.md 需包含：
- frontmatter `requiredTools`：包含 `Read`、`Edit`、`Write`、`Bash` 以及 `mcp__github__*` 等 GitHub 操作工具（或透過 `gh` CLI Bash 呼叫）
- 輸入格式契約：定義 Issue 至 User Story 的轉化流程
- injection 防護步驟：引用本 ADR 決策域三的 XML 隔離標記要求

### 對 skills/schedule/SKILL.md 的影響

§15 使用範例區塊需新增 `/schedule backlog-intake` 的 cron 範例，含 ADR-005 規格 Pre-flight 步驟（Pre-flight 項目 1-5 驗證）。

### 對 PRODUCT_BACKLOG.md 的影響

backlog-intake 執行後會 append 新的 Story 條目至 PRODUCT_BACKLOG.md 的「未排程」區段。PO 需定期審查並精化這些自動入庫的 Story（補充 AC、估算 Size、排入 Sprint）。

### 對維運的影響

- OAuth token 過期（claude CLI 與 gh CLI 均適用）：排程執行失敗，log 中出現認證錯誤；處理方式為 `claude auth login` 或 `gh auth login` 重新認證
- `backlog-intake` label 管理：PO 需在需要入庫的 Issues 上手動添加 `backlog-intake` label；可透過 GitHub automation（Issue template、GitHub Actions）自動添加

## Decision Challenge（QA Engineer）

**挑戰**：決策域三「injection 防護邊界」引入了「輸出格式強制限制」作為 ADR-006 的補充邊界，要求 AI subagent 的輸出限定為預定義的 Markdown 表格格式。此要求在 ADR 層面提出，但沒有可驗證的測試覆蓋（AC4 為靜態文件條件）。若 AI 在邊緣情況下產生格式超出預期的輸出，SKILL.md 的實作需要有明確的輸出驗證步驟，否則此防護邊界只是文件聲明而非實際控制。

**反駁**：此挑戰正確識別了靜態文件防護的局限性。三點說明：第一，backlog-intake 的輸出格式限制屬於 SKILL.md 實作層的職責，ADR-009 在架構層面確立「必須有輸出驗證步驟」的要求，SKILL.md 實作時需在格式轉化步驟後加入格式驗證（以正則或 Markdown 表格行格式檢查）。第二，backlog-intake 的最終寫入目標（PRODUCT_BACKLOG.md）為 PO 日常查看的核心文件，格式異常具有高可見性，不屬於靜默失敗場景。第三，US-63 明確為 [靜態] 類型（AC1-AC4 均為文件類型），測試覆蓋屬於後續 Implementation Story 的範疇，本 ADR 的任務是確立架構決策而非實作驗證。
