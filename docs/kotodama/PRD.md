# Kotodama（言霊）— Product Brief

> v0.2.0 | 2026-03-17 | Owner: Product Owner | Status: Draft

## 產品願景

每個軟體產品配一位 AI 產品經理 -- 在客戶熟悉的聊天管道中，用自然語言收集需求、釐清模糊、產出 User Story，超出職權時自動升級給人類。

每個產品部署一套獨立實例，資料完全隔離。

## 目標用戶

- **產品負責人**：在通勤、會議間隙用 LINE 丟想法，期望有人幫整理成可執行的需求
- **產品經理**：需要在多方之間協調需求，希望 AI 先做初步彙整和追問，自己專注策略性決策
- **業務人員**：面對客戶時需要快速查產品規格、確認需求進度

## 核心使用場景

### 場景 1：多人協作提出新需求

1. 老闆在 LINE 說：「報表匯出應該支援 PDF」
2. AI 判斷為新需求，開啟 30 秒多人輸入收集窗口
3. 業務在 Slack 補充：「特別是季度報表，客戶嫌 Excel 不好看」
4. 窗口關閉，AI 彙整所有人的輸入，同步推送到所有管道
5. AI 追問模糊點（最多 3 輪），收斂後產出 User Story + AC
6. 相關人確認後，需求進入 CONFIRMED 狀態

### 場景 2：升級到人類 PM

1. 客戶問到報價、合約、技術承諾等超出 AI 職權的問題
2. AI 明確告知無法回答，同時通知人類 PM（含完整脈絡摘要）
3. 人類 PM 介入處理，AI 繼續處理職權內的部分
4. 問題解決後，人類 PM 將控制權交還 AI

## MVP 功能清單

MVP 目標：驗證 AI 能否有效擔任產品經理角色，在多管道環境中收集和釐清需求。

規模：5 個試點產品，每產品 3-5 位用戶，2 個管道（LINE + Slack）。

### P0 -- Must Have

- **實例部署**：用 template 部署獨立實例，每實例獨立 DB
- **對話狀態機**：IDLE > EXPLORING > CLARIFYING > DRAFTING > REVIEWING > CONFIRMED（MVP 到此為止，後續狀態 Phase 2 再做）
- **LINE 管道**：收發訊息，支援文字和圖片
- **Slack 管道**：收發訊息，支援 Thread 和 Block Kit
- **共享對話空間**：跨管道訊息匯聚，彙整結果同步推送，標註來源
- **需求釐清**：AI 追問模糊點，最多 3 輪未收斂則升級
- **User Story 生成**：產出 As a / I want / So that 格式，附 AC
- **升級機制**：偵測超出職權的問題，通知人類 PM，含脈絡摘要
- **多人輸入收集**：30 秒窗口收集多人輸入，彙整為統一摘要

### P1 -- Should Have（Phase 2 再評估）

- Telegram / Web Chat 管道
- 產品知識庫查詢（pgvector 語意搜尋）
- 需求進度查詢
- Shikigami 工程銜接
- 對話歷史搜尋

## 安全邊界

AI 可以存取的資料：
- 功能清單、規格文件、API 能力描述
- 需求狀態、Backlog、Sprint 進度
- 當前實例的對話歷史和決策紀錄

AI 不可存取的資料：
- 原始碼、API 實作細節、架構文件
- 其他實例的任何資訊
- 成本、報價、合約（除非明確授權）
- Credentials、密鑰、Token
- 生產環境資料、基礎設施配置

實作方式：禁止的 tool 不出現在 LLM tool schema，從源頭阻斷。

## 升級機制

觸發升級的情境：
- 涉及報價、合約、法律問題
- 涉及技術承諾（時程、可行性保證）
- AI 追問 3 輪仍無法收斂需求
- AI 信心不足的判斷

升級時 AI 的行為：
- 明確告知客戶「這個問題我無法回答，已通知 [人名] 來處理」
- 發送升級通知給指定人類 PM，附完整對話脈絡摘要
- 繼續處理職權內的其他對話，不中斷服務

## 里程碑

### Phase 1：MVP（第 1-10 週）

- 基礎設施：實例部署 template、NATS JetStream、Claude API 串接
- 核心流程：對話狀態機、需求釐清、User Story 生成、升級機制
- 管道：LINE + Slack
- 交付：5 個試點產品上線

### Phase 2：擴展（第 11-20 週）

- 新增 Telegram + Web Chat 管道
- 產品知識庫查詢
- 進度查詢與主動通知
- 基於 Phase 1 回饋的迭代改善

### Phase 3：工程銜接（第 21 週以後）

- Shikigami 整合，需求確認後驅動 Sprint
- 完整的狀態流程（SCHEDULED > IN_PROGRESS > DELIVERED）
- 規模化到 50 個產品實例

## 關鍵風險

1. **客戶接受度**：客戶是否願意跟 AI 而非人類討論需求？Plan B 是改為 AI 輔助模式（人類主導，AI 側邊建議）
2. **LLM 能力邊界**：Claude API 的理解能力是否足以擔任 PM 角色？Plan B 是增加人類審核環節
3. **升級判斷準確度**：AI 可能該升級沒升級，或過度升級。策略是寧可多升級，再逐步調寬

## 技術棧

- TypeScript + Fastify
- NATS JetStream（訊息匯流排）
- PostgreSQL + pgvector（每實例獨立 DB）
- Claude API（LLM 引擎）
- K3s（容器編排）
