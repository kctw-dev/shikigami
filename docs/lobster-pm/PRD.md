## 1. 產品願景與目標

### 願景

讓每個軟體產品都有一位永不下班的 AI 產品經理——在客戶熟悉的通訊管道中，用自然語言收集需求、釐清模糊、產出規格、追蹤進度，並在需求成熟時自動驅動工程團隊交付。

### 產品定位

Lobster PM 是一個多租戶 AI 產品經理平台，同時服務約 100 個產品。每個產品的多位利害關係人（老闆、PM、工程師、業務等）透過 LINE / Slack / Telegram / Web Chat / Email 等管道，與專屬的 AI 產品經理互動。AI 產品經理負責需求釐清、User Story 撰寫、進度回報，並在需求確認後驅動 Shikigami 框架的工程團隊執行開發。

### 核心價值主張

| 對象 | 痛點 | Lobster PM 帶來的價值 |
|------|------|----------------------|
| 產品負責人 | 需求散落在各管道，難以彙整 | 統一對話空間，AI 自動彙整所有人的輸入 |
| 開發團隊 | 需求描述模糊，來回確認耗時 | AI 主動追問並產出結構化 User Story + AC |
| 業務/客戶 | 不知道需求進度，需要反覆詢問 | 即時回報需求狀態，主動通知里程碑 |
| 平台營運方 | 100 個產品各需專屬 PM，人力不可能 | AI 規模化，一個平台服務所有產品 |

### 商業目標

- **BG-1**：在上線 6 個月內，承載 50 個以上活躍產品
- **BG-2**：將需求從「初始提出」到「User Story 確認」的平均時間縮短 60%
- **BG-3**：減少 80% 的「需求描述不清導致返工」

## 3. 使用場景

### 場景 1：多人協作提出新需求

**前提**：SaaS 產品「TaskFlow」已在 Lobster PM 上架，老闆 Victor 用 LINE，PM Mia 用 Slack，業務 Alex 用 Telegram。

**流程**：

1. Victor 在 LINE 發訊息：「我覺得報表匯出應該支援 PDF，客戶一直在問。」
2. AI 產品經理收到訊息，判斷這是新需求，進入 **EXPLORING** 狀態。
3. 30 秒的多人輸入收集窗口開啟。
4. Alex 在 Telegram 補充：「對，特別是季度報表，客戶說 Excel 不好看給老闆。」
5. 窗口關閉後，AI 彙整兩人的輸入，產出初步需求摘要並發送到所有管道。
6. AI 進入 **CLARIFYING** 狀態，追問：「請問 PDF 報表需要包含哪些資料區塊？是否需要自訂 Logo 和配色？有沒有已知的報表範本可以參考？」
7. Mia 在 Slack 回覆：「先做月報和季報就好，要能放客戶 Logo。」
8. AI 進入 **DRAFTING** 狀態，產出 User Story 和 AC。
9. 三人在各自管道確認或補充。
10. AI 進入 **REVIEWING** 狀態，所有人確認後進入 **CONFIRMED**。

**驗收標準**：
- 三個管道的訊息在同一個對話脈絡中被彙整
- 彙整結果同步推送到所有管道
- User Story 包含所有人的輸入，不遺漏

### 場景 2：需求升級到人類 PM

**前提**：客戶在討論一個功能時涉及報價。

**流程**：

1. Victor 問：「這個 PDF 報表功能如果要加上白標（White Label），加購價格怎麼算？」
2. AI 產品經理偵測到「報價」關鍵字，判斷超出職權範圍。
3. AI 回覆：「報價問題我無法直接回答，已經通知 Mia 來處理。在她回覆之前，我可以先繼續整理功能規格的部分。」
4. 系統發送升級通知給 Mia（含完整對話脈絡摘要）。
5. Mia 選擇 **Assist** 模式介入，在 Slack 回覆報價資訊。
6. AI 繼續處理功能規格的部分，Mia 的報價回覆同步到所有管道。
7. 當報價問題解決後，Mia 將控制權交還 AI。

**驗收標準**：
- AI 正確辨識超出職權的問題類型
- 升級通知包含完整脈絡，人類 PM 不需要從頭了解
- 三種介入模式（Takeover / Assist / Override）運作正確
- 控制權交還後 AI 能延續之前的對話狀態

### 場景 3：需求成熟驅動工程執行

**前提**：PDF 報表匯出需求已進入 CONFIRMED 狀態。

**流程**：

1. AI 產品經理將確認的 User Story + AC 打包成結構化的需求包。
2. AI 檢查 TaskFlow 產品的 Sprint 排程，建議排入下一個 Sprint。
3. Mia 確認排程後，需求進入 **SCHEDULED** 狀態。
4. 系統透過 NATS JetStream 將需求包發送給 TaskFlow 的 Shikigami 工程團隊。
5. Shikigami Scrum Master 收到需求，啟動 Sprint Planning。
6. 需求進入 **IN_PROGRESS** 狀態，AI 產品經理定期查詢 Sprint 進度。
7. Victor 在 LINE 問：「報表功能做到哪了？」
8. AI 查詢 Sprint Board，回覆：「目前在 Sprint 12，已完成 3/5 個子任務，預計本週五可以進入 QA 測試。」
9. 開發完成後，需求進入 **DELIVERED** 狀態，AI 主動通知所有管道。

**驗收標準**：
- 需求包格式符合 Shikigami 框架的輸入規範
- 進度查詢反映即時的 Sprint 狀態
- 狀態變更主動通知到所有管道

### 場景 4：產品知識查詢

**前提**：業務 Alex 正在與客戶通話，需要快速確認功能細節。

**流程**：

1. Alex 在 Telegram 問：「我們的 API 有支援批次匯入嗎？一次最多幾筆？」
2. AI 產品經理透過 pgvector 語意搜尋，從產品知識庫找到相關規格文件。
3. AI 回覆：「有的，TaskFlow API 支援批次匯入，單次最多 1,000 筆。相關的 API 文件連結是 [link]。需要注意的是，超過 500 筆建議使用非同步模式。」
4. Alex 追問：「客戶想匯入 5,000 筆歷史資料，有什麼建議做法？」
5. AI 回覆：「建議分批處理，每批 500 筆，使用非同步模式。如果需要一次性匯入的功能，可以作為新需求提出，要我現在建立嗎？」

**驗收標準**：
- AI 僅回覆產品知識庫中有的資訊，不虛構
- 查詢不會觸及原始碼或實作細節
- 無法確認的問題明確告知並提供替代方案

## 5. 非功能需求

### 5.1 安全性

| ID | 需求 | 指標 |
|----|------|------|
| NFR-S01 | 租戶資料隔離 | 三層防禦全部通過滲透測試，零跨租戶資料洩漏 |
| NFR-S02 | AI 知識邊界控制 | 禁止存取的資料類型（原始碼、credentials 等）在 tool schema 中不存在 |
| NFR-S03 | 通訊加密 | 所有管道通訊使用 TLS 1.3，靜態資料 AES-256 加密 |
| NFR-S04 | 身份驗證 | 每個管道有獨立的身份驗證機制，支援 OAuth 2.0 |
| NFR-S05 | 審計日誌 | 所有資料存取操作記錄審計日誌，保存 90 天 |

### 5.2 效能

| ID | 需求 | 指標 |
|----|------|------|
| NFR-P01 | 訊息回應延遲 | AI 首次回應在 5 秒內（P95），完整回覆在 15 秒內（P95） |
| NFR-P02 | 並行處理 | 同時處理 100 個產品的對話，無效能退化 |
| NFR-P03 | 訊息吞吐量 | 支撐每分鐘 500 則訊息的峰值流量 |
| NFR-P04 | 知識查詢延遲 | pgvector 語意搜尋在 500ms 內返回結果（P95） |

### 5.3 可用性

| ID | 需求 | 指標 |
|----|------|------|
| NFR-A01 | 系統可用性 | 99.5% uptime（每月停機不超過 3.6 小時） |
| NFR-A02 | 訊息不遺失 | NATS JetStream 保證 at-least-once delivery |
| NFR-A03 | 優雅降級 | 單一管道故障不影響其他管道，AI 服務不可用時有人工接手流程 |
| NFR-A04 | 資料備份 | PostgreSQL 每日全量備份，RPO < 1 小時 |

### 5.4 可維護性

| ID | 需求 | 指標 |
|----|------|------|
| NFR-M01 | 新管道上線 | 新增一個管道適配器不超過 2 個工作天 |
| NFR-M02 | 新產品上架 | 從建立到可用不超過 30 分鐘 |
| NFR-M03 | 可觀測性 | 結構化日誌 + 分散式追蹤 + 指標監控（Metrics / Logs / Traces 三支柱） |

## 6. MVP 範圍定義

### MVP 做什麼

MVP 的目標是驗證核心假設：**AI 可以有效地擔任產品經理角色，在多管道環境中收集和釐清需求。**

**納入 MVP 的功能**：
- F-001：多租戶產品管理（支援 5 個產品即可）
- F-002：對話狀態機（完整九個狀態）
- F-003：管道適配 — LINE
- F-004：管道適配 — Slack
- F-005：共享對話空間
- F-006：需求釐清與追問
- F-007：User Story 生成
- F-008：安全隔離 — 三層防禦
- F-009：升級機制
- F-010：多人輸入收集與彙整

**MVP 的規模**：
- 5 個試點產品
- 每個產品 3-5 位活躍用戶
- 2 個管道（LINE + Slack）

### MVP 不做什麼

| 明確排除 | 理由 |
|----------|------|
| Telegram / Web Chat / Email 管道 | 先驗證核心流程，管道可後續擴充 |
| 產品知識庫語意搜尋 | MVP 專注需求收集，知識查詢為第二優先 |
| 工程銜接自動化（Shikigami 驅動） | MVP 先驗證需求端，工程端用人工銜接 |
| 平台管理 Web UI | MVP 用 CLI / API 管理即可 |
| 多語言支援 | MVP 僅支援繁體中文 |
| AI 品質分析 | MVP 用手動抽查替代 |
| RICE 自動計算 | MVP 由人類 PM 手動排序 |

## 7. 成功指標（KPIs）

### North Star Metric

**需求收斂率（Requirement Convergence Rate）**：從需求初始提出到 User Story 確認（CONFIRMED 狀態）的成功比例。目標 > 80%。

### 核心 KPIs

| 類別 | 指標 | 目標 | 量測方式 |
|------|------|------|---------|
| **效率** | 需求收斂時間 | 初提出到 CONFIRMED 平均 < 48 小時 | 狀態機時間戳差值 |
| **效率** | AI 追問輪數 | 平均 < 3 輪即收斂 | 對話狀態轉換計數 |
| **品質** | User Story 一次通過率 | > 70% Story 不需人類 PM 修改 | REVIEWING 到 CONFIRMED 無修改的比例 |
| **品質** | 升級處理率 | 升級案件 100% 在 4 小時內被人類接手 | 升級通知到人類首次回應時間 |
| **滿意度** | 客戶滿意度 | NPS > 30 | 定期問卷調查 |
| **採用** | 月活躍產品數 | MVP 期間 5 個，全面上線後 50+ | 每月有對話活動的產品數 |
| **採用** | 日均對話量 | 每個產品每日 > 3 則有效對話 | 訊息計數（排除系統通知） |
| **安全** | 跨租戶資料洩漏 | 零事件 | 安全審計 + 滲透測試 |

### Funnel Metrics

```
訊息輸入 → 需求辨識 → 需求探索 → 需求釐清 → Story 生成 → Story 確認 → 排程 → 交付
  100%       85%         75%         60%         50%          40%        35%     30%
```

每個階段的轉換率是優化的重點。目標是在 6 個月內將 **訊息輸入 → Story 確認** 的端到端轉換率從 40% 提升到 60%。

## 8. 風險與假設

### 假設

| ID | 假設 | 驗證方式 | 失敗時的 Plan B |
|----|------|---------|----------------|
| A-01 | 客戶願意在即時通訊中與 AI（而非人類）討論需求 | MVP 試點的採用率和留存率 | 改為 AI 輔助模式（人類 PM 主導，AI 側邊建議） |
| A-02 | Claude API 的理解能力足以擔任 PM 角色 | 需求收斂率和 Story 品質指標 | 增加 prompt 工程投入，或引入人類審核環節 |
| A-03 | 30 秒的多人收集窗口是適當的時長 | 觀察窗口內/外訊息比例 | 改為動態窗口（偵測到多人發言時延長） |
| A-04 | 共享對話空間不會造成資訊過載 | 客戶滿意度和對話參與度 | 引入主題分流（每個需求獨立 Thread） |
| A-05 | 100 個產品可以用同一套 prompt 和行為模式 | 各產品的 Story 品質差異 | 支援 per-product 的 prompt 模板客製化 |

### 風險

| ID | 風險 | 影響 | 可能性 | 緩解策略 |
|----|------|------|--------|---------|
| R-01 | Claude API 延遲或不穩定導致對話體驗差 | 高 | 中 | 實作回應快取、fallback 模型、逾時優雅降級 |
| R-02 | AI 對超出職權的問題判斷錯誤（該升級沒升級，或過度升級） | 高 | 中 | 用分類器輔助判斷 + 持續標注訓練 + 寬鬆升級策略（寧可多升級） |
| R-03 | 多管道同步延遲造成對話脈絡不一致 | 中 | 中 | NATS JetStream 保證順序，管道適配器加 retry |
| R-04 | 租戶隔離出現漏洞 | 嚴重 | 低 | 三層防禦 + 定期滲透測試 + 隔離驗證的自動化測試 |
| R-05 | 規模擴展到 100 產品時效能瓶頸 | 高 | 中 | 早期壓力測試、水平擴展設計、LLM 呼叫佇列管理 |
| R-06 | 管道 API 變更（LINE / Slack 改版）導致適配器失效 | 中 | 中 | 管道適配器抽象層設計，減少耦合 |
| R-07 | LLM 產出的 User Story 品質不穩定 | 高 | 中 | 建立 Story 品質評估模型，低品質自動觸發人類審核 |
