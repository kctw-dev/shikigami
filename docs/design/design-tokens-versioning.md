# Design Tokens 版本控制策略

**文件狀態**：正式
**建立日期**：2026-03-06
**來源 Story**：US-132（Sprint 54）
**關聯設計檔**：`docs/design/design-tokens.json`

---

## 1. 目的

本文件定義 `design-tokens.json` 的版本控制策略，確保：

- 設計 Token 的每次變更都有明確的版本號追蹤
- UIUX 管線的輸出成品可回溯至生成時使用的 Token 版本
- Token 的破壞性變更（breaking change）有明確的通知與升版規則

---

## 2. 版本號格式（Semantic Versioning）

採用 **Semantic Versioning（semver）** 規範：

```
MAJOR.MINOR.PATCH
```

### 2.1 版本號遞增規則

| 版本段 | 觸發條件 | 範例 |
|--------|----------|------|
| MAJOR | 移除既有 Token 鍵名 / 大規模重命名（破壞性變更） | `1.0.0` → `2.0.0` |
| MINOR | 新增 Token 類別或鍵名（向下相容） | `1.0.0` → `1.1.0` |
| PATCH | 修正 Token 值（如色碼微調、描述文字更新） | `1.0.0` → `1.0.1` |

### 2.2 初始版本

`design-tokens.json` 的初始版本為 `1.0.0`，代表 ADR-014 Phase 1 規格定義完成且已進入穩定狀態。

---

## 3. 變更記錄規則

### 3.1 變更記錄位置

每次 Token 版本升版時，必須同步更新以下位置：

1. **`design-tokens.json`**：更新頂層 `version` 欄位
2. **本文件 §5 變更日誌**：新增變更記錄條目

### 3.2 變更記錄格式

每筆變更記錄須包含：

```markdown
## v{MAJOR.MINOR.PATCH} — {YYYY-MM-DD}

### 變更類型
- [新增 / 修改 / 移除] {Token 路徑}：{變更說明}

### 影響範圍
- {受影響的元件或使用場景}

### 遷移指引（MAJOR 升版必填）
- {舊鍵名} → {新鍵名}（或標注「已移除」）
```

### 3.3 審查要求

| 變更類型 | 審查要求 |
|----------|----------|
| PATCH 變更 | 開發者自行確認，PR 描述說明即可 |
| MINOR 變更 | 需 UI Designer 確認新 Token 命名符合設計系統慣例 |
| MAJOR 變更 | 需 Architect + Product Owner 聯合審查，並發佈遷移通知 |

## 4. Token 版本與管線輸出的可追溯性

### 4.1 可追溯性原則

UIUX 管線（shikigami:ui）在生成前端代碼時，必須在輸出成品的 metadata 或 comment 中記錄使用的 Token 版本。

範例（生成的前端代碼 header comment）：

```javascript
/**
 * Generated by shikigami:ui
 * Design Tokens Version: 1.0.0
 * Generated At: 2026-03-06
 * Story: US-XXX
 */
```

### 4.2 版本鎖定規則

- **鎖定（Lock）**：每個前端 Story 的生成結果應記錄產出時的 Token 版本號
- **回溯（Rollback）**：若需回溯至舊版 Token，透過 git history 查詢 `design-tokens.json` 的歷史版本
- **diff 工具**：使用 `git diff {commit-a}..{commit-b} -- docs/design/design-tokens.json` 比較 Token 版本差異

### 4.3 CI 驗證（規劃中）

未來 CI 流程應驗證：
- PR 中 `design-tokens.json` 的 `version` 欄位是否已按規則遞增
- 生成的前端代碼 metadata 中的 Token 版本與當前版本是否一致
