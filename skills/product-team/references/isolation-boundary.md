# 隔離邊界 — 預設隔離、例外互通

## 1. 這條規則在解什麼問題

多 agent 架構最常見的失敗不是「agent 不夠聰明」，而是**context 共享不良導致決策互相衝突**：A 假設了一件事、B 假設了相反的事，兩邊各自做完，合起來壞掉。

有兩種相反的處方：

- **全部共享**：讓每個 agent 看到所有人的產出。結果是 context 爆炸、雜訊淹沒訊號，且晚做的 agent 被早做的 agent 錨定
- **全部隔離**：每個 agent 拿自包含任務、全新 context、不知道其他人存在。結果是需要協商的議題無法協商

本 Skill 採**預設隔離、例外互通**：隔離是常態，互通要有明確理由。

---

## 2. 預設隔離（S / M 檔，以及 L 檔的實作階段）

每個 teammate 收到：

1. **自包含任務描述** —— 不需要看別人的產出就能開工
2. **指定輸出格式** —— lead 才有辦法機械式地合併
3. **全新 context window** —— 不繼承 lead 對話歷史
4. **不知道其他 teammate 存在** —— 不主動 message 任何人

lead 負責合併。teammate 之間的一致性由**任務拆解時的邊界設計**保證，不是靠他們臨時協商。

拆解時若發現「這兩個 task 必須互相知道對方怎麼做」，那代表**邊界畫錯了**——把它們合併成一個 task 給同一個人，或改成串行 pipeline。這比開放互通便宜得多。

---

## 3. 例外互通（只有這三種）

開放 mailbox 讓 teammate 互相 message，僅限：

### 3.1 root cause 不明的除錯

單一 agent 找到第一個看似合理的解釋就停了。這是 anchoring：一旦某個理論被探索過，後續調查會偏向它。

解法是讓多個調查者**各持不同假設、互相試圖證偽**。活下來的理論才可能是真的 root cause。

派工範本：

```
使用者回報 {症狀}。
Spawn {N} 個 teammate 調查不同假設。讓他們互相對話、試圖證偽對方的理論，
像科學辯論一樣。把浮現的共識寫進 {findings 檔案}。
```

關鍵在**「試圖證偽對方」**這句。少了它，agent 會禮貌性地互相同意。

### 3.2 架構方案取捨

需要正反論證的技術決策。開放互通讓 Architect 與 Developer 就可行性來回，避免出現「架構上優雅但實作上不可行」的 ADR。

限制：只對**該議題**開放，不是整個 session 都開著。

### 3.3 review 意見衝突

兩個 reviewer 對同一段程式碼給出矛盾建議時，讓他們直接收斂，不要讓 lead 猜。

---

## 4. 不該開放互通的情況

| 情況 | 為什麼不 |
|------|----------|
| 「讓他們互相同步進度」 | 進度同步是 lead 和 task list 的職責 |
| 「讓 QA 問 Developer 怎麼實作的」 | 這正是要避免的實作偏見 |
| 「反正開著也沒差」 | 每則訊息都是 token，且會錨定收訊方 |
| 平行實作階段 | 邊界應該已經切乾淨，需要溝通代表切錯了 |

---

## 5. 辯論模式的收斂條件

開了辯論就要有停止條件，否則會無限來回：

- **達成共識** → 記錄結論與理由，結束
- **兩輪後仍分歧** → 停止辯論，各方立場交給 lead，由 lead 或人類裁決
- **偏離原議題** → 立即中止

辯論輪次上限預設 2。這不是為了省事——超過兩輪還沒收斂，通常代表缺的是資訊不是論證，再辯也沒用。

---

## 6. 未啟用 Agent Teams 時

沒有 mailbox 就沒有辯論模式。此時：

- lead 分別收集各方**獨立**意見（這仍有價值，去除了錨定）
- lead 自行收斂
- **報告中必須標注「未經對抗驗證」**

不得假裝辯論發生過。獨立意見的平均 ≠ 對抗後的共識。
