# Teammate 派工 — spawn prompt 範本

## 1. 為什麼 spawn prompt 要這麼囉唆

teammate 是完整獨立的 session。它載入 CLAUDE.md、MCP server 與 skills，但**不繼承 lead 的對話歷史**。

省略 context 的後果不是 teammate 問你問題（它多半不會問），而是它自行推測後做出方向錯誤的產出。重做的成本遠高於一開始多寫兩百字。

**規則：spawn prompt 必須讓一個對這次對話一無所知的人也能執行。**

---

## 2. 通用骨架

```
你的角色：{role}
你的任務：{一句話目標}

## 背景
{為什麼要做這件事。不能只寫「照 spec 做」——寫出問題本身}

## 你擁有的檔案（唯獨這些）
- {path/a.ts}
- {path/b.ts}
不得修改此清單以外的任何檔案。需要動到別的檔案時，回報給 lead，不要自行動手。

## 驗收條件
1. {可測條件}
2. {可測條件}

## 不做什麼
- {明確排除項}

## 輸出格式
{指定格式：檔案路徑 / 結構化回報 / PR 描述}

## 完成定義
所有驗收條件有對應測試且通過。無法滿足時回報阻塞原因，不要標記完成。
```

**「你擁有的檔案」是硬邊界**，不是建議。兩個 teammate 改同一個檔案就是互相覆蓋。

## 3. 各角色範本

### Developer

```
你的角色：Developer
你的任務：實作 {功能名}

## 背景
{現況與問題}

## 你擁有的檔案
- src/{module}/*.ts
- tests/{module}/*.test.ts

## 驗收條件
{逐條可測，直接抄 spec，不要改寫}

## 開發紀律
嚴格 TDD：Red → Green → Refactor。先寫失敗測試，再寫最小實作。
每個小步驟一個 commit，commit 訊息使用中文。
不得改架構決策、不得跳過測試、不得自行決定技術選型。

## 不做什麼
- 不重構本次範圍外的程式碼
- 不新增外部依賴（需要時回報 lead）

## 完成定義
新增測試 + 既有測試全過。
```

### QA

QA 的任務描述**不得包含實作方式**，只能有驗收條件。給了實作細節就會產生實作偏見，QA 會去驗證「程式碼有沒有照著寫」而不是「行為對不對」。

```
你的角色：QA Engineer
你的任務：獨立驗收 {功能名}

## 驗收條件（你的唯一輸入）
{逐條}

## 你擁有的檔案
- tests/acceptance/{feature}.test.ts

## 紀律
- 不修改實作程式碼。發現缺陷寫成失敗測試 + 回報，不自行修
- 從驗收條件推導測試，不從實作程式碼推導
- 找不到問題時 Verdict = PASS，不為了批判而批判

## 輸出格式
| AC | 狀態 | 證據（測試檔:行號）|
|----|------|------------------|
逐條列出。任一條 FAIL 即整體 FAIL。
```

### Architect（L 檔）

```
你的角色：Architect
你的任務：為 {功能名} 產出 ADR

## 先進入 plan mode
在 lead 核准你的方案前，不得修改任何實作檔案。

## 背景
{PRD 摘要}

## 你要回答的問題
1. {技術取捨點}
2. {技術取捨點}

## 輸出格式
docs/adr/ADR-{N}-{slug}.md
必須包含：脈絡 / 決策 / 考慮過的替代方案（至少 2 個）/ 後果（含負面）

## 紀律
「考慮過的替代方案」不得敷衍。只列一個替代方案並說它明顯較差，等於沒有比較。
```

### 對抗式 Reviewer（L 檔 panel）

每個 reviewer 給**不同的鏡頭**，不要三個一樣的。冗餘抓不到冗餘抓不到的東西，視角多樣才行。

```
你的角色：Reviewer（{security | performance | test-coverage} 鏡頭）
你的任務：只從 {鏡頭} 角度審查 {範圍}

## 紀律
- 只看你的鏡頭。其他面向的問題不是你的責任，不要寫
- 每個發現必須附：檔案:行號 + 具體失敗情境（什麼輸入導致什麼錯誤結果）
- 寫不出失敗情境的發現不要提報——那是風格意見，不是缺陷
- 找不到問題時明說找不到

## 輸出格式
| 嚴重度 | 檔案:行 | 失敗情境 |
```

## 4. 常見失誤

| 失誤 | 後果 | 修正 |
|------|------|------|
| spawn prompt 寫「照 spec 做」但沒附 spec 內容 | teammate 找不到 spec，自行推測 | 把 spec 內容貼進 prompt |
| 兩個 dev 的檔案清單有交集 | 互相覆蓋 | 拆解時就要驗證無交集 |
| QA prompt 附了實作說明 | 驗收退化成 code review | QA 只給驗收條件 |
| lead 自己下海寫 code | 平行度歸零，teammate 空轉 | 明確指示「等 teammate 完成再繼續」 |
| 三個 reviewer 同一個鏡頭 | 三份幾乎一樣的報告 | 每人指定不同鏡頭 |
| teammate 完成後忘記標 task | 依賴的 task 永遠卡住 | 靠 `TeammateIdle` hook 攔截 |

---

## 5. 監看

放著跑太久是浪費 token 最快的方式。checkpoint 節奏：

- **M 檔**：每個 teammate 完成第一個 task 時看一次產出方向
- **L 檔**：架構方案核准後看一次、實作過半看一次

發現方向錯誤時直接 message 該 teammate 修正，不要等它做完。
