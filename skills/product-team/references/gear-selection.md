# 換檔判定 — 完整流程與範例

## 1. 為什麼要客觀規則

讓 lead「自行判斷複雜度」等於沒有規則。實測上 agent 傾向高估任務複雜度、傾向多派人，因為多派人在它的效用函數裡沒有代價——代價落在使用者的 token 帳單上。

L 檔約消耗 S 檔的 10-15 倍 token。這不是估算誤差，是多 agent 架構的固有成本：每個 teammate 有自己的 context window，成本隨在線人數線性成長，協調訊息則超線性成長。

因此換檔必須用**可被第三方複核的訊號**，而且必須**輸出理由**。

---

## 2. 判定流程

```
起點：S 檔
  │
  ├─ 跑 R1：需求寫得出驗收測試嗎？
  │    否 → 中止換檔，轉 Product Analyst 釐清需求
  │    是 → 繼續
  │
  ├─ 跑 U1..U5：任一命中？
  │    是 → 升一檔（S→M，M→L）。命中多條仍只升一檔
  │    否 → 繼續
  │
  ├─ 跑 D1..D3：全部命中？
  │    是 → 降一檔（下限 S）
  │    否 → 維持
  │
  ├─ 跑 R2：命中 U5 且使用者未明確授權？
  │    是 → 停止，向人類確認
  │
  └─ 輸出：「檔次 = X，命中 Un/Dn，理由 = ...」
```

**升檔只升一檔。** 命中三條 U 不代表跳三檔——多重訊號代表這件事確實不小，但 L 檔已經是上限，S 檔命中多條也只到 M 檔。若在 M 檔又命中新的 U 條款（例如做到一半才發現要改 schema），此時才升到 L。

---

## 3. 條款細則

### U1：觸及檔案 > 5 個

以**預估會被修改的檔案**計，不含只讀取的檔案。無法預估時先做一次探索，探索本身走 S 檔。

邊界情況：批次改名 50 個檔案 —— 檔案數超標但屬機械性操作，同時命中 D3（純格式調整），依 §2 流程 D 需全部命中才降檔，D1 不成立，故維持升檔後的 M 檔。**這是刻意的**：大批次機械操作出錯時影響面很大，值得一個獨立驗收者。

### U2：跨層

前端 / 後端 / DB 至少兩層。判準是「改動需要同時理解兩種以上的執行環境」。

不算跨層：後端改了 API 回傳欄位、前端只是跟著改型別定義（單向、機械性）。
算跨層：新增功能需要同時設計 API 契約、DB 欄位與前端狀態管理。

### U3：對外契約

public API、DB schema、事件格式、設定檔格式、CLI 介面、plugin manifest。判準是「repo 外部的人會不會因為這個改動而壞掉」。

### U4：新增外部依賴

新的 package、新的服務、新的 MCP server。既有依賴升版不算，除非跨 major。

### U5：不可逆

資料遷移、刪除操作、對外發布（npm publish / release tag）、金流、寄信給真人、寫入生產資料庫。

命中 U5 時**同時觸發 R2**，必須向人類確認，不因為 `project_level=low` 而豁免。`project_level=low` 的自動執行原則適用於流程推進，不適用於不可逆的外部副作用。

### D1..D3：降檔

三條全中才降，因為降檔會移除獨立驗收者，風險不對稱——多派一個人的代價是 token，少派一個人的代價是缺陷進 main。

## 4. 範例

### 範例 A：修正 README 錯字

- R1：可測（檔案內容比對）→ 通過
- U1..U5：全不命中
- D1（單檔案不跨層）✓、D2（無測試但屬 D3 範疇）、D3（純文件）✓
- **判定：S 檔。理由 = 命中 D1/D3，無 U 條款**

### 範例 B：新增使用者頭像上傳

- R1：可測 → 通過
- U1：預估 7 個檔案 ✓
- U2：前端上傳元件 + 後端儲存 + DB 欄位 ✓
- U3：新增 API endpoint ✓
- U4：需要圖片處理套件 ✓
- **判定：M 檔（S 升一檔）。理由 = 命中 U1/U2/U3/U4**

若此功能在 M 檔執行中發現需要遷移既有使用者資料 → 命中 U5 → 升 L 檔，且觸發 R2 向人類確認。

### 範例 C：「把搜尋做得更好用一點」

- R1：寫不出驗收測試 —— 「更好用」未定義
- **判定：中止換檔。轉 Product Analyst 釐清，列出可能解讀（搜尋速度？結果相關性？篩選器？）與各自的驗收條件**

這是最重要的一類。加人解決不了需求不清，只會讓五個 agent 各自朝五個方向發揮。

---

## 5. 輸出格式

換檔判定必須輸出這一行，供人類複核：

```
gear=M  triggers=U1,U2,U3,U4  roster=analyst,dev×2,qa  isolation=full  est=3-4x
```

命中 R 條款時：

```
gear=HALT  triggers=R1  reason=「更好用」不可測，需釐清
```
